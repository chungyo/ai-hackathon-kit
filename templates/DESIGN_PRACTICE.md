# 설계 이해 연습: 요구에서 재현 가능한 검증까지

이 문서는 시험 답안이 아니라 준비용 학습 예시다. 가상의 서비스와 정책을 사용한다. 실제 과제에서는 원문·데이터 계약·담당자 답변이 기준이며 이 예시의 정책을 그대로 적용하지 않는다. 시험 중 AI, 자료 열람 및 후속 서술형에 대한 최신 규정을 따른다.

## 1. PRD, 설계, 구현, 검증은 서로 어떻게 다른가?

| 단계 | 답해야 하는 질문 | 결과 |
| --- | --- | --- |
| PRD | 누가 무엇을 해야 하며 무엇이 성공인가? | 사용자 행동·조건·인수 기준 |
| 설계 | 어떤 입력과 상태를 어떤 규칙으로 처리하는가? | 데이터 흐름·경계·실패 시 상태·선택 근거 |
| 구현 | 설계가 코드에서 실제로 어떻게 동작하는가? | 함수·API·DB·UI |
| 검증 | 특정 입력에서 무엇이 실제로 관측됐는가? | 재현 가능한 절차·결과·미검증 범위 |

예를 들어 “유효하지 않은 입력을 거절한다”는 요구만으로는 사용자에게 표시할 오류, DB 변경 여부, 이전 결과를 어떻게 볼지 모두 정해지지 않는다. 원문에 명시되지 않은 정책은 질문하거나 가정으로 표시한다.

## 2. 가상 과제: 담당자의 데이터셋 적용과 결과 생성

가상 원문: “담당자는 준비된 데이터셋을 선택하고 적용해 결과를 생성한다. 잘못된 데이터셋은 적용하지 않으며 기존 데이터와 결과를 보존한다. 다른 데이터셋을 적용한 후에는 그 데이터의 결과를 새로 생성해야 한다.”

이 예시에서 데이터셋은 A 또는 B이고 결과 생성은 시간이 걸릴 수 있다고 가정한다. **과제 원문에서 동시 요청에 대한 정책은 명시되지 않았으므로 아래 정책은 설계 연습을 위한 선택이다.**

### PRD: 무엇이 성공인가?

| ID | 요구 / 사용자 | 인수 기준 |
| --- | --- | --- |
| R1 | 담당자가 유효한 데이터셋을 적용 | 검증된 데이터셋이 현재 데이터로 표시된다. |
| R2 | 잘못된 데이터셋 거부 | 실패 이유를 표시하고 현재 데이터와 기존 결과를 보존한다. |
| R3 | 새 데이터셋을 적용한 뒤 결과 생성 | 결과가 어떤 데이터셋으로 생성됐는지 알 수 있고 과거 결과를 새 결과로 표시하지 않는다. |

### 설계: 어떤 상태와 관계가 필요한가?

```text
데이터셋 A 적용 → A로 결과 생성 → 데이터셋 B 적용 → B로 재계산

현재 데이터셋: A 또는 B
결과의 출처: 결과를 만든 데이터셋 식별자
계산 상태: 대기 / 진행 중 / 성공 / 실패 (실제 구현에 맞게 정의)
```

- 현재 데이터셋과 생성 결과에 그 출처 식별자를 기록한다.
- 유효성 확인이 실패하면 현재 데이터와 기존 결과를 변경하지 않는다.
- B 적용 후 A 결과는 보관될 수 있으나 B에 대한 최신 결과로 표시하지 않는다.
- 화면에 보이는 안내와 DB에 남은 데이터는 별도로 확인한다.

이 구조의 목적은 과거 결과를 무조건 삭제하는 것이 아니라, **어떤 데이터로 만든 결과인지 식별하고 현재 결과와 혼동하지 않게 하는 것**이다. 실제 과제의 삭제·보관 정책이 있다면 그것을 우선한다.

### 동시 요청: 구체적 선택과 보장 지점

가상 상황: A로 계산을 시작한 뒤 관리자가 B를 적용했고, A의 계산이 나중에 끝난다.

연습용 선택: 계산 시작 때 A의 식별자를 기록하고, 결과 저장 시점에 현재 데이터셋이 여전히 A인지 확인한다. 여전히 A일 때만 A 결과를 현재 결과로 등록한다. B로 변경됐다면 A 결과는 현재 결과로 등록하지 않고 작업이 오래된 입력에 기반했음을 알린다.

여기에는 중요한 구현 조건이 있다. **현재 식별자를 확인하는 동작과 결과를 현재 결과로 등록하는 동작은 같은 트랜잭션 등의 원자적 처리 또는 조건부 갱신으로 묶어야 한다.** 확인과 저장 사이에 B가 적용될 수 있다면 확인만 해서는 경합을 막지 못한다. 사용한 DB와 저장 구조가 이 조건을 실제로 보장하는지 따로 확인해야 한다.

다른 선택도 가능하다. 예를 들어 계산 중 데이터셋 적용을 서버에서 거부하거나 대기시킬 수 있다. 어떤 정책이 맞는지는 과제의 운영 조건에 달려 있다. 브라우저 버튼만 잠그면 다른 탭이나 직접 API 호출을 막을 수 없으므로 서버 측 보장과는 구분한다.

### 검증기: 무엇을 확인하고 무엇을 확인하지 않는가?

가상 검증기의 역할을 명시적으로 정한다.

| 항목 | 검증 범위 예시 |
| --- | --- |
| 확인 | 결과의 데이터셋 식별자가 계산 입력과 일치하는지, 결과 필수 항목이 있는지 |
| 별도 확인 필요 | 계산 자체가 업무상 정확한지, UI가 오래된 결과를 숨기는지, 실제 동시 요청에서 저장이 안전한지 |
| 근거 | 원문·확인된 업무 규칙·입력과 결과. 생성 함수의 반환값을 그대로 정답으로 삼지 않는다. |

검증기를 분리했다고 해서 완전히 독립적인 것은 아니다. 같은 조건식이나 같은 잘못된 가정을 공유하면 둘 다 같은 오류를 놓칠 수 있다. 작은 입력을 사람이 직접 계산한 기대값과 비교하거나 별도의 테스트 데이터로 확인하면 검증 범위를 넓힐 수 있다. 다만 수행하지 않았다면 그 검증은 미실행이다.

### 구현과 검증을 연결하는 사례

| 사례 | 전제와 실행 | 기대 결과 | 확인할 관측 | 상태 |
| --- | --- | --- | --- | --- |
| 무효 데이터 | A와 A 결과가 있는 상태에서 잘못된 B 적용 | B 거부, A와 A 결과 보존 | 응답·화면·DB 전후 | 미실행 예시 |
| 데이터 변경 | A 결과가 있는 상태에서 유효한 B 적용 | B가 현재 데이터. A 결과를 B의 결과로 표시하지 않음 | 현재 데이터·결과 출처·화면 | 미실행 예시 |
| 동시성 | A 계산 시작 → B 적용 → A 계산 종료 | 위의 연습용 정책대로 A 결과는 현재 결과로 등록되지 않음 | 시간순 요청, 최종 DB·응답·화면 | 미실행 예시 |

동시성 테스트는 요청 순서만 나열하는 것으로 충분하지 않다. 테스트에서 계산을 의도적으로 멈추고 B를 적용한 뒤 계산을 끝내는 등 실제 경합 구간을 제어하고, 최종 DB를 확인해야 한다. 실제로 그렇게 실행하지 않았다면 동시성 검증 통과로 쓰지 않는다.

## 3. AI와 함께 일할 때 남길 사실

한 건의 실제 판단에 대해 다음을 기록한다.

```text
문제와 알게 된 경로: [원문 / 데이터 / 담당자 답변]
AI의 제안: [실제 제안]
내 판단: [실제로 수용·수정·기각한 것과 이유]
확인: [입력과 실행 방법, 실제 결과]
한계: [확인하지 못한 것]
```

AI의 제안을 반드시 고치거나 버려야 하는 것은 아니다. 실제로 수용만 했다면 수용 근거와 검증을 설명한다. 일어나지 않은 수정, 질문, 테스트를 만들어내지 않는다.

## 4. 실제 과제에서 재사용할 질문

- 이 기능의 입력, 결과, 저장되는 상태는 각각 무엇인가?
- 성공과 실패 시 사용자가 보는 것과 실제 데이터는 각각 어떻게 바뀌는가?
- 요청이 겹치면 어떤 결과를 허용하며 서버의 어느 지점에서 보장하는가?
- 결과를 만들어내는 규칙과 결과를 검사하는 규칙은 무엇이며 어떤 한계가 있는가?
- 원문·담당자 답변·가정·AI 제안·내 결정은 각각 무엇인가?
- 다른 사람이 어떤 입력과 명령 또는 조작으로 주장을 재현할 수 있는가?
