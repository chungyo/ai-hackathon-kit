# 처음 보는 과제를 푸는 실전 절차

## 목적과 적용 범위

문제 내용을 미리 가정하지 않고, 시험 중 사용할 판단 순서와 AI 협업 방식을 준비한다. 문제를 이해하고 구현을 주도하는 것은 응시자의 역할이다. 서술형은 실제 선택과 증거에 근거해 본인이 설명한다. 시험 환경에서의 자료 열람·AI 사용·후속 서술형 규정은 최신 지시를 따른다.

이 문서는 연습용 절차다. 시간은 3시간 시험을 가정한 예시이며 실제 지시와 제한에 맞춰 조정한다. 키트 반입, 공개 저장소 접근, 외부 네트워크 및 패키지 설치 허용은 보장되지 않는다.

## 전체 흐름

```text
문제·환경 파악 → 요구사항과 질문 → 짧은 PRD → 스택 선택·설계
→ 한 기능씩 구현 + 즉시 확인 → 요구별 검증 → 실행·제출·설명 확인
```

작업판은 [WORKBOOK.md](WORKBOOK.md), 지시문은 [PROMPTS.md](PROMPTS.md)를 사용한다. 작성은 진행하면서 갱신하고 문서 작업이 코딩과 검증을 대체하지 않게 한다.

## 0~15분: 문제와 제공 환경 확인

**직접 할 일**

1. 원문을 읽으며 사용자·목적·필수 기능·제약·제출물을 표시한다.
2. 제공된 문서, 데이터 명세, 출력 계약, 시작 코드가 있으면 살펴본다.
3. 고쳐서는 안 되는 파일, 허용 도구, 실행·제출 방법을 확인한다.
4. 답이 달라지면 구현도 달라지는 질문을 분리해 담당자에게 보낸다. 답과 무관한 작업은 계속한다.

**AI에 맡길 일**: 실제로 읽은 자료를 근거로 요구사항·질문 초안을 만들고 원문 위치를 표시하게 한다. 없는 데이터나 정책을 지어내지 않게 한다.

**다음 단계로 갈 조건**: 무엇이 필수이고 무엇이 미확정인지 말할 수 있다. 답을 기다리는 항목은 대기 상태로 둔다.

## 15~30분: 짧은 PRD와 스택 결정

**PRD의 최소 내용**

| 항목 | 작성할 내용 |
| --- | --- |
| 문제·사용자 | 누가 어떤 상황에서 무엇을 하려는가 |
| 핵심 흐름 | 시작 → 입력·행동 → 결과 |
| 요구사항 | 원문 출처·필수 조건·역할·입출력 |
| 인수 기준 | 구체적인 전제 → 행동 → 기대 결과 |
| 미확정 | 담당자 질문·답변·설계에 미치는 영향 |

**결정**: 제공 코드·런타임·제출 형식·문제의 핵심 계산·익숙함을 함께 보고 아래 스택 선택 기준을 적용한다. 선택과 이유를 2~3줄로 기록한다.

**AI에 맡길 일**: PRD 초안과 스택 비교안을 요구사항에 연결해 만들게 한다. 필수 요건을 선택 사항으로 바꾸거나 정해지지 않은 정책을 확정하지 않았는지 직접 확인한다.

**다음 단계로 갈 조건**: 사용자의 핵심 행동과 결과, 반드시 지켜야 할 규칙, 기술 선택 이유를 말할 수 있다. 상세 정책을 모르면 미확정으로 둔다.

## 30~45분: 구현 가능한 설계

과도한 아키텍처 문서보다 다음 다섯 가지를 만든다.

1. **흐름**: 화면 입력 → API/서버 → 검증·처리 → 데이터 저장 → 결과 화면.
2. **데이터**: 실제 제공 형식과 저장할 정보, 필요한 식별자·상태.
3. **기능 계약**: 해당 기능의 입력, 출력, 권한, 정상·실패 시 데이터 상태.
4. **예외**: 과제에 관련된 오류·중복 요청·결과 없음과 화면/서버/DB의 처리.
5. **작업 순서**: 핵심 흐름을 작은 단위로 나누고 각 단위의 확인 방법을 연결.

기술 그림은 사용하는 스택에 맞춰 최소한으로 적는다. 실제 문제에 없는 인증, 큐, 여러 서버, 복잡한 최적화 패키지를 무조건 추가하지 않는다. 결과 생성과 검증을 구분하되, 결과 검증이 실제로 무엇을 확인하는지 따로 적는다.

**다음 단계로 갈 조건**: 첫 번째 사용자 행동을 입력부터 결과까지 어떻게 연결할지 설명할 수 있다.

## 45~135분: 작은 단위의 구현과 확인

각 기능에서 아래를 반복한다.

1. 요구 ID·입력·기대 결과를 지정하고 AI에 한 단위 구현을 요청한다.
2. 코드의 주요 흐름과 AI가 추가한 가정을 확인한다.
3. 관련 정상 사례와 중요한 실패 또는 경계 사례를 실제로 확인한다.
4. 실행 방법·관측 결과·미검증을 작업판에 남긴다.
5. 다음 필수 기능을 구현한다.

여기서 말하는 한 단위는 UI만 또는 DB만 만드는 것이 아니라, 가능한 범위에서 사용자 행동이 입력 → 처리 → 결과까지 이어지는 작은 기능이다. 제공 API·DB나 사용자 화면이 필수라면 실제 연결을 확인한다. 조건에 맞지 않는 모의 성공을 실제 성공으로 표현하지 않는다.

시간을 쓸수록 미완료 필수 요구를 다시 확인한다. 디자인 장식이나 근거 없는 확장 때문에 필수 검증·제출 시간이 사라지지 않게 한다.

## 135~165분: 전체 검증

- 원문의 모든 필수 요구와 구현·확인 근거를 다시 대조한다.
- 대표 정상 흐름을 처음부터 끝까지 실행한다.
- 문제에서 중요한 데이터 오류·권한·계산 경계·저장 실패·경합 중 해당하는 것을 점검한다.
- 저장이 요구되면 결과 재조회와 재시작 후 상태를 실제로 확인한다.
- 출력 스키마와 제출 파일·실행 방식·Docker 등 요구된 항목을 확인한다.
- 생성 로직의 확인 결과와 별도 검증 결과의 범위를 구분한다.

조건 하나가 검증되지 않았다면 전체 요구를 통과로 표시하지 않는다. 테스트 더블 통과와 실제 DB·화면·컨테이너 확인도 구분한다.

## 165~180분: 정리와 설명

- 지정된 파일에 실행 방법·설정·실제 제한을 기록한다.
- 작업 중 실제로 발생한 핵심 문제, AI 제안, 본인 판단, 테스트와 관측을 정리한다.
- 필수 요구별 미완료·미검증을 표시하고 제출물을 확인한다.
- 입력 → 처리 → 저장/출력, 선택 이유, 실패 시 상태를 본인 말로 설명해 본다.

## 스택 선택 기준: Next.js 단독 vs React + FastAPI

현재 두 스택의 경험이 비슷하므로 기본 후보는 연결 부담이 적은 **Next.js 단독**이다. 이것은 연습 전의 가설이며 어떤 스택이 더 빠른지 측정한 결과가 아니다. 제공 코드와 실제 과제가 기본 후보보다 우선한다.

| 판단 항목 | Next.js 단독 | React + FastAPI |
| --- | --- | --- |
| 적합한 출발점 | 화면·일반 API·저장 중심, Node로 계산 가능한 과제 | Python의 데이터 처리·계산 도구가 실제로 필요한 과제 |
| 개발 언어 | 주로 TypeScript 한 가지 | React의 TypeScript/JavaScript와 Python |
| 연결·실행 | 프런트와 API를 같은 Next 앱에서 구성 가능 | 프런트·API를 연결해야 하며 실행·빌드 방식 설계 필요 |
| API 사용 | Route Handler 등으로 API 제공 | FastAPI 요청 검증·자동 API 문서 활용 가능 |
| 인증·배포 | 서버 권한 검증과 환경 설정 필요 | API 인증·프런트 연결·환경 설정 필요 |
| 신경 쓸 부분 | 큰 CPU 계산, 서버 런타임, 파일/DB의 영구성 | 두 런타임, API 주소, 다른 origin인 경우 CORS·쿠키, 컨테이너 구성 |

FastAPI를 쓰는 경우도 React 정적 빌드물을 FastAPI에서 제공하거나 프록시를 두는 등 구성 방식이 여럿이다. 무조건 두 컨테이너나 CORS가 필요한 것은 아니다. 과제에 `Dockerfile` 하나로 실행하라는 요구가 있는지, Compose가 허용되는지도 확인한다. Python이나 별도 서버가 필요하지 않은데 서비스를 늘리지 않는다.

### 빠른 선택 질문

1. 제공된 코드·필수 런타임이 정해져 있는가? **그 조건을 따른다.**
2. Python 전용 또는 이미 제공된 Python 계산 코드·필수 라이브러리가 문제 해결에 중요한가? **그렇다면 React + FastAPI를 우선 검토한다.**
3. 핵심 계산을 TypeScript로 충분히 구현할 수 있고 연결을 단순화하는 편이 유리한가? **그렇다면 Next.js 단독을 우선 검토한다.**
4. 양쪽이 모두 가능하다면? **동일 과제를 미리 측정한 결과와 시험 환경에서 사용 가능한 설치·빌드 방식을 기준으로 정한다.**

CPU 중심의 오래 걸리는 작업은 어느 쪽이든 요청 처리와 자원을 막을 수 있다. 선택만으로 해결된다고 가정하지 말고 실제 데이터·실행 환경에서 시간을 재고 필요한 처리 방식을 정한다. 외부 라이브러리 설치나 네트워크 허용 여부도 확인한다.

### 2회 비교 연습: 같은 범위를 같은 조건으로

아직 어느 스택이 빠른지는 측정하지 않았다. 준비 환경에서 다음 범위를 양쪽으로 각각 만들어 본다.

- 화면 입력 → 서버 검증 → DB 저장 → 재조회.
- 무효 입력 거부와 저장 실패 시 결과 확인.
- 요구 시 설정 주입·초기화·헬스체크·컨테이너 빌드 및 재시작 확인.
- 실행 안내와 실제 검증 결과 기록.

같은 문제·필수 기준·데이터·제한 시간으로 비교하고, 언어/도구 초기 경험 및 사전 준비 차이를 기록한다. 각 회차마다 시작부터 실제로 확인된 완료까지 걸린 시간, 막힌 지점, 구현 누락, 통합 오류, 본인이 설명하지 못하는 부분을 기록한다. 한 번의 결과로 일반화하지 않고, 시간이 허락하면 순서나 문제를 바꿔 다시 비교한다. 시험 환경과 패키지 캐시는 연습 환경과 다를 수 있다.

| 항목 | Next.js | React + FastAPI |
| --- | --- | --- |
| 실행 준비 ~ 핵심 흐름 검증 시간 | 미측정 | 미측정 |
| 필수 요구 구현·검증 누락 | 미측정 | 미측정 |
| 연결·인증·설정·Docker 문제 | 미측정 | 미측정 |
| 내 말로 설명하지 못한 지점 | 미측정 | 미측정 |

## AI 작업 요청의 기본 형식

```text
[현재 단계]에서 [요구 ID와 원문 조건]을 다뤄 줘.
확정된 사실과 미확정 가정을 구분해 줘.
입력 → 처리 → 결과와 실패 시 상태를 제시해 줘.
내가 확인해야 할 결정, 대안과 이유, 실제 검증 방법을 설명해 줘.
실제로 실행하지 않은 것은 미검증으로 표시해 줘.
```

AI가 제안했다고 자동으로 채택하지 않는다. 확인한 출처, 판단, 실제 테스트 결과를 작업 중 짧게 기록해 두면 나중에 자신의 말로 설명할 근거가 된다. AI의 제안을 수정·기각한 적이 없다면 그런 경험을 지어내지 않는다.
