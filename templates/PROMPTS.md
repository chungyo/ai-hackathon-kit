# 단계별 AI 지시문

시험 중 AI·자료 사용이 허용되는 경우에만 사용한다. 제공 파일 경로는 실제 과제에 맞게 바꾸고, 존재하지 않는 파일은 만들어 읽은 척하지 않는다. 한 번에 전체 구현을 맡기지 않고 각 단계의 결과와 근거를 확인한다. 사용자가 직접 판단해야 하는 업무 질문과 규칙은 AI의 추정으로 확정하지 않는다.

## 0. 시작: 환경과 규칙

```text
과제 지시와 제공된 문서, 데이터 설명, 출력 계약, 기존 작업 상태를 먼저 확인해 줘.
시험 환경·제출·보존해야 할 파일·금지 사항과 필수 산출물을 정리해 줘.
아직 코드나 원문 파일은 수정하지 마.
없는 파일이나 확인하지 못한 내용은 추정하지 말고 미확인으로 표시해 줘.
```

내 확인: 실제 읽은 자료와 규칙이 맞는가? 제출물과 수정 금지 파일을 놓치지 않았는가?

## 1. 분석: 요구사항과 질문

```text
과제 원문을 기준으로 요구사항을 임시 ID로 정리해 줘.
각 항목에 원문 출처, 사용자·행동·조건·결과, 필수 여부, 검증 가능한 인수 기준을 붙여 줘.
데이터·권한·실패 처리·출력·실행·제출 요구도 누락하지 마.
확정 사실, 추론, 미확정 정책을 구분하고 서로 충돌하는 조건을 표시해 줘.
담당자에게 물어볼 업무 질문과 답에 따라 달라질 구현을 중요도순으로 제안해 줘.
근거 없는 정책과 수치는 만들지 말고 아직 구현하지 마.
```

내 확인: 각 요구가 원문에 있는가? 어떤 답변이 어떤 구현을 바꾸는가? 필수를 선택으로 바꾸지 않았는가?

## 2. PRD·설계: 한 번에 구현할 수 있는 범위로

```text
확인한 요구와 실제 담당자 답변을 바탕으로 간결한 PRD와 설계를 만들어 줘.
사용자 핵심 흐름, 입력·처리·출력, 데이터 변경, 실패 시 상태,
요구 ID별 인수 기준, 질문·가정·결정을 포함해 줘.
제공된 실행 환경과 기존 코드, 내가 익숙한 기술을 우선하고
가능한 단순한 기술 구성과 중요한 대안·트레이드오프를 제안해 줘.
필수 기능을 작은 세로 단위로 나누고 각 단위의 검증 방법을 적어 줘.
확인되지 않은 계약이나 정책은 미확정으로 남겨 줘.
핵심 기능의 정상·입력 오류·처리 실패·동시 요청·결과 없음 중 관련 상황을 골라
각 상황의 화면, 응답, DB 상태와 이전 결과의 유효성을 따로 설명해 줘.
검증 로직이 확인하는 조건과 확인하지 않는 조건을 구분하고,
가능하면 생성 코드와 다른 관점의 재현 가능한 기준 사례를 제안해 줘.
```

내 확인: 내가 설명할 수 있는 구조인가? 기존 환경에서 실행 가능한가? 핵심 필수 흐름을 놓치지 않았는가? 서로 다른 요청이 겹칠 때 실제 서버가 어떤 규칙을 보장하는가?

## 3. 구현: 한 기능씩

```text
요구 [ID]의 [구체적 사용자 행동]부터 구현해 줘.
시작 상태, 입력, 서버 검증·처리, 출력과 저장 상태까지 연결해 줘.
기존 작업을 보존하고 요청과 무관한 변경은 하지 마.
실제 데이터와 계약을 사용하고 mock이 필요하면 실제 연결과 분리해 표시해 줘.
작업 후 실행한 검증, 실제 결과, 미검증 사항을 보고해 줘.
다른 기능으로 넘어가기 전에 이 요구의 입력→처리→결과, 관련 파일·함수,
선택 이유와 실패 시 상태를 쉬운 말로 설명해 줘.
실제 실행한 테스트의 명령·대표 입력·기대와 관측, 확인 수준을 알려 주고,
내가 직접 설명할 핵심을 한두 문장으로 정리해 줘.
실행하지 않은 테스트나 내가 내리지 않은 판단은 만들지 마.
```

내 확인: 화면만 만들어진 것은 아닌가? 실제 입력과 데이터 상태가 연결됐는가? AI가 추가한 가정은 무엇인가?

Next.js App Router에서 데이터 검증·저장·재계산을 다룬다면 백엔드 스킬의 `references/NEXT_DATA_WORKFLOW.md`를 실제 경로로 읽게 한다. 학습 예제의 데이터 형식이나 결과를 실제 과제의 계약으로 쓰지 않는다.

## 4. 테스트: 반례와 상태 확인

```text
구현된 [요구 ID]를 원문과 확정된 계약에 대조해 줘.
정상, 무효 입력, 중요한 경계, 실패·복구와 권한 중 실제로 해당하는 사례를 고르고
각 사례의 전제, 입력, 기대 결과와 근거, 실제 검증 방법을 제시해 줘.
저장 기능은 응답뿐 아니라 데이터 전후와 별도 재조회를 확인해 줘.
실행 가능한 검증은 실행하고, 실행하지 않은 항목은 미검증으로 표시해 줘.
테스트 더블과 실제 서비스·DB 검증을 구분해 줘.
```

내 확인: 기대값이 실제 요구에서 나왔는가? 실패 경로가 실제로 실행됐는가? 관측 결과는 무엇인가?

## 5. 오류 수정: 증상부터 재검증까지

```text
[실제 입력·기대 결과·관측 결과·오류]를 바탕으로 원인을 조사해 줘.
관련 경계를 따라 근거를 확인하고 추정과 확인된 원인을 구분해 줘.
원문과 기존 데이터에 맞는 최소 범위로 수정한 뒤
가능하면 같은 재현 조건과 관련 정상 조건을 다시 확인해 줘.
실제로 실행한 결과와 여전히 확인하지 못한 점을 보고해 줘.
```

내 확인: 원인이 증거로 확인됐는가? 같은 조건에서 수정이 확인됐는가? 테스트를 통과시키려고 요구를 약화하지 않았는가?

## 6. 최종 대조: 제출과 설명

```text
과제 원문의 모든 필수 요구와 제출물을 기준으로 현재 상태를 감사해 줘.
요구 ID별 구현 위치, 실제 확인 방법과 관측, 통과·실패·미검증을 구분해 줘.
필수 조건 하나라도 확인하지 못했다면 전체 요구를 통과로 표시하지 마.
실행 문서와 출력 형식, 재시작·실제 연결·화면 확인 중 요구된 항목을 점검해 줘.
내가 직접 설명해야 할 데이터 흐름, 선택 근거, 실제 장애·검증과 남은 한계를 질문으로 정리해 줘.
실제로 발생하지 않은 경험이나 실행하지 않은 테스트를 만들어내지 마.
```

내 확인: 요구별 증거가 있는가? 실행과 제출 방법이 재현 가능한가? 내가 직접 이유와 한계를 설명할 수 있는가?

## 7. 이해 확인: 내 말로 설명하기

시험 준비 중 허용된 환경에서 사용한다. 사진의 질문 문구나 작성된 답변을 외우는 대신 실제 작업을 설명하는 연습이다.

```text
내가 구현한 [기능]을 기준으로 PRD의 요구에서 실제 코드와 검증까지
입력 → 처리 → 상태 변화 → 결과 흐름을 한 번에 한 질문씩 물어봐 줘.
내 답변이 불완전하면 확인되지 않은 내용을 만들어내지 말고 작은 힌트를 줘.
특히 실패 시 기존 데이터, 겹친 요청, 결과가 없을 때의 상태,
검증기의 확인 범위와 실제 재현 방법을 질문해 줘.
AI 제안 중 내가 실제로 수용·수정·기각한 것이 있다면 그 이유를 물어봐 줘.
```
