# Next.js App Router 백엔드 실전 가이드

과제에서 Next.js App Router를 실제로 사용하는 경우에만 읽는다. 이 문서는 **문제 해결과 작동 검증을 위한 안내**이며 과제 README·제공 코드·실제 버전·시험 규정보다 우선하지 않는다. 예시 API·필드·정책은 가상이다. 개인 키, 외부 AI·클라우드 연결, 배포, 시험 데이터 외부 전송 및 제한 우회는 하지 않는다.

## 1. 먼저 프로젝트를 확인한다

- `package.json`, lockfile, `app/` 또는 `src/app/`, `pages/`, 기존 `api/*/route.ts`, `lib/`, DB client, 테스트 파일과 실제 실행 명령을 확인한다. 이력이나 기존 파일을 지우지 않는다.
- App Router인지 Pages Router인지와 `next`의 설치 버전을 파악한다. 아래 `app/api/.../route.ts`는 App Router용이다. Pages Router라면 `pages/api`와 해당 버전의 기존 패턴을 따른다.
- `package.json`의 `scripts`와 lockfile 기준으로 기존 패키지 매니저·테스트·타입 검사·빌드 명령을 선택한다. 패키지명·스키마·인증 방식·DB 연결이 없으면 임의로 설치하거나 설정하지 않는다.
- 과제에서 명시한 method·경로·요청/응답·에러·저장·데이터 규칙을 표로 적는다. 화면이 보여야 한다는 것과 API·저장이 실제로 동작해야 한다는 것은 별개의 요구다.

## 2. 어떤 서버 경로를 쓰나

| 요구 | 우선 확인할 방식 | 주의 |
| --- | --- | --- |
| 외부 클라이언트/FE가 호출하는 HTTP API | `app/api/<resource>/route.ts`의 Route Handler | URL, method, 상태 코드, 인증/인가·입력 검증 |
| Server Component의 최초 데이터 조회 | 기존 서버 데이터 함수·DB를 직접 호출하는지 확인 | 자기 Route Handler를 HTTP로 재호출하지 않아도 되는지 검토 |
| React 폼에서 서버로 변경 요청 | 프로젝트에 Server Action/Function 패턴이 있으면 사용 가능 | 인증·인가와 서버 입력 검증을 해당 작업 안에서도 수행 |
| Pages Router의 API | `pages/api/*` 기존 코드·버전 | App Router의 `route.ts`와 혼용해 계약을 바꾸지 않기 |

서버 함수 공유와 Route Handler 응답 생성은 구분한다. 서버 컴포넌트에서 자기 Route Handler를 호출하는 방식은 빌드 시 리스닝 서버 부재와 불필요한 HTTP 왕복 문제가 생길 수 있으므로 기존 구조와 실제 실행 조건을 확인한다. FE가 HTTP 계약을 요구하면 Route Handler는 여전히 필요하다.

## 3. Route Handler와 요청 경계

`app/api/orders/route.ts`의 `GET`/`POST`가 `/api/orders`에 대응한다. `app/api/orders/[id]/route.ts`는 상세 경로다. 동일 경로 세그먼트에서 `page.tsx`와 `route.ts`가 충돌할 수 있으므로 기존 파일을 먼저 확인한다.

- JSON: `await request.json()`은 잘못된 JSON에서 실패할 수 있다. 파싱 오류와 필드 검증 오류를 실제 계약에 맞게 처리한다. 요청 본문은 기본적으로 한 번 소비하므로 중복 읽기를 피한다.
- 쿼리: `new URL(request.url).searchParams.get('q')`는 없으면 `null`; 숫자 변환 시 빈 문자열·NaN·범위를 실제 정책에 따라 구분한다.
- 동적 경로: 현재 공식 문서는 `await context.params`를 사용한다. 이전 Next 버전과 타입이 다를 수 있으므로 **설치된 버전·기존 코드**를 먼저 확인하고 패턴을 맞춘다.
- 파일 업로드가 명시된 경우에만 `request.formData()`와 `File`을 사용한다. 파일 크기·형식·권한·일부 실패 정책은 과제/계약을 확인한다. 시험의 개인 PC 파일 업로드 금지를 우회하거나 임의의 외부 업로드 서비스를 사용하지 않는다.
- Route Handler는 HTTP로 접근 가능한 진입점이다. 보호가 필요한 경우 기존 세션 확인과 리소스 권한 확인을 서버에서 수행한다. 버튼을 숨기는 것, 화면 진입 검사 또는 미들웨어/Proxy만으로 모든 서버 작업이 보호된다고 가정하지 않는다.

## 4. 검증 가능한 POST 예시

[로컬 계산 예시](../examples/next-calculation/route.ts)는 외부 통신·DB 없이 정수 입력을 검증해 결과를 계산한다. 예시 정책은 `quantity`, `unitPrice`가 0 이상의 안전한 정수이며, 범위를 벗어난 결과는 거부하는 것이다. **이 정책·경로·응답 형식은 실제 과제에 그대로 적용할 기준이 아니다.**

- 파싱 실패 → 400; 객체가 아닌 입력 → 400; 누락·음수·문자열·소수 → 400; 안전하지 않은 곱셈 결과 → 400; 정상 입력 → 200과 `{total}`.
- 예상 가능한 입력 오류와 예상하지 못한 저장 오류를 구분한다. 실제 과제의 상태 코드·오류 구조가 있으면 그것을 유지한다. 스택·토큰·사용자 입력 전문을 응답이나 로그에 포함하지 않는다.
- 이 예시에는 저장, 인증, 서버 실행, 실제 Next 라우팅이 없다. 이 테스트가 통과해도 이 기능들이 구현됐거나 작동한다고 주장하지 않는다.

### FE에서 호출할 때

실제 API가 `/api/calculation`이고 위 예시 계약일 때만 참고한다. 값은 사용자로부터 받으며 API 주소와 데이터는 과제 계약에 따라 조정한다.

```ts
const response = await fetch('/api/calculation', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ quantity: 2, unitPrice: 5000 }),
});
const payload = await response.json();
if (!response.ok) {
  // 화면에 오류를 보여 주고 입력을 유지한다. 서버 저장 성공으로 처리하지 않는다.
  throw new Error(typeof payload.error === 'string' ? payload.error : '처리에 실패했습니다.');
}
// 실제 계약에 맞게 payload.total을 표시한다.
```

`fetch`는 4xx/5xx에서 보통 예외를 던지지 않으므로 `response.ok`를 확인한다. 중복 제출·로딩·오류는 기존 FE 패턴을 따른다. 실제 응답과 mock 응답을 구분한다.

## 5. 저장, 서버 상태, 인증

| 상황 | 할 일 | 확인할 증거 |
| --- | --- | --- |
| 제공된 DB/ORM이 있음 | 기존 client·모델·migration 정책을 읽고 기존 방식으로 접근 | 실제 요청 후 저장된 값과 재조회 |
| DB 설정이 없거나 접속이 차단됨 | 임의의 DB/클라우드/개인 키를 추가하지 말고 계약과 환경을 확인 | 연결 오류, 미구현·미검증과 영향 |
| 둘 이상의 쓰기가 한 단위로 성공해야 함 | 기존 DB의 트랜잭션을 고려하고 실패 시 상태를 검증 | 전부 저장 또는 요구한 롤백 상태 |
| 중복 요청이 중요한 쓰기 | 기존 계약의 중복 방지·키·상태 전이를 확인 | 같은 요청을 반복했을 때 관측 결과 |
| 사용자별 보호 데이터 | 기존 인증 방식과 리소스별 인가를 Route Handler/Action에서도 검증 | 미인증·타인 리소스 거부와 저장 상태 |

서버 프로세스의 변수나 로컬 파일은 재시작·인스턴스 분리·배포 환경에 따라 사라지거나 공유되지 않을 수 있다. 과제가 영속 저장을 요구하면 인메모리 배열을 완성품으로 제시하지 않는다. DB 상태를 확인할 수 없다면 모의 테스트와 실제 연결 미검증을 구분한다.

### 저장 기능의 구현 순서

1. 기존 DB 정의에서 대상 모델·필수 필드·고유 제약·관계를 확인하고, 과제 API의 입력과 어떤 필드로 연결되는지 정한다.
2. 요청 JSON 파싱 → 타입/필수값/업무 정책 검증 → 필요할 때 인증·인가 → 기존 DB client 쓰기 → 계약된 응답 순으로 연결한다. 검증 실패 시 DB 쓰기를 시작하지 않는지 확인한다.
3. 같은 값을 다시 보냈을 때의 동작, 대상이 없을 때의 처리, 변경이 여러 테이블에 미치는 영향은 실제 요구와 DB 제약에서 확인한다. 기존 DB에서 테이블을 지우거나 임의로 migration·seed를 실행하지 않는다.
4. 정상 요청 뒤 실제 데이터 값과 재조회 결과를 확인한다. 의도적으로 실패를 검증할 수 있는 안전한 테스트 환경에서는 실패 후 데이터가 변경되지 않았는지도 확인한다. 실제 운영 데이터에 오류 주입·삭제는 하지 않는다.
5. 특정 ORM·SQL 명령을 정확히 모르면 lockfile·schema·기존 구현과 해당 버전의 제공 문서부터 확인한다. DB 연동이 없는데 가상의 client 이름을 코드에 넣고 구현 완료로 주장하지 않는다.

### 실제 구현 전 계약 카드

하나의 쓰기 기능을 시작할 때 아래를 제공 코드·과제 근거로 채운다. 정보가 없으면 빈칸을 임의 확정하지 말고 확인 대상으로 남긴다.

| 경계 | 확인할 내용 | 구현·검증 시 주의 |
| --- | --- | --- |
| 진입 | App/Pages Router, method·경로, 소비하는 FE | 기존 계약이 이미 있으면 요청 형식과 응답 래퍼를 유지 |
| 입력 | content type, 필수 필드, 타입·단위·업무 조건 | 잘못된 JSON과 필드 거부를 구분; 값의 0·빈 문자열·누락을 혼동하지 않음 |
| 신뢰 | 세션, 호출자의 역할, 접근 대상 소유권 | 필요한 경우 서버의 Handler/Action에서 확인; UI의 버튼 숨김은 인가 증거가 아님 |
| 변경 | 대상 모델·필드·상태 전이·여러 쓰기의 관계 | 실패 시 유지돼야 할 데이터 상태와 기존 트랜잭션 경계 확인 |
| 응답 | 상태 코드, 성공·오류 본문, FE 필드 | 계약 없는 메시지·상태 코드를 확정하지 않음; 내부 오류·비밀 노출 금지 |
| 재조회 | 저장 후 조회 경로와 최신 데이터 조건 | 성공 응답과 실제 저장·재조회는 별도로 확인 |

### 동시 요청·재시도·부분 실패

- 같은 키의 동시 요청에서 단 하나의 기록만 허용해야 한다면 `조회 후 없으면 생성`만으로는 두 요청이 동시에 조회를 통과할 수 있다. 실제 요구와 기존 DB의 고유 제약·트랜잭션·충돌 처리를 확인하고 안전한 테스트 데이터로 결과를 관찰한다. 모든 쓰기에 중복 방지 기능을 새로 추가하라는 뜻은 아니다.
- 두 레코드 변경이 하나의 업무 단위로 성공해야 한다면 한쪽만 저장된 상태를 허용하는지 확인한다. 요구가 원자성을 요구하고 기존 DB가 지원하면 트랜잭션을 사용하고, 격리된 테스트에서 두 번째 쓰기 실패 후 상태를 검증한다. 둘 이상의 시스템에 걸친 작업은 단일 DB 트랜잭션으로 모두 롤백된다고 가정하지 않는다.
- 클라이언트가 쓰기 응답을 받기 전에 타임아웃되면 **실패와 성공 어느 쪽도 확정할 수 없다**. 결과 확인 방법과 기존 중복 방지 계약을 살핀 뒤 재시도한다. 자동 재시도·중복 허용 여부는 실제 과제 정책에 따른다.

### 가상 요청 하나를 끝까지 추적

가상의 요구: `POST /api/items`는 `{name}`을 받고 실제 저장 뒤 `{item}`을 응답한다. 이 예시는 실제 과제 스키마가 아니다.

1. 제공된 Next 버전과 `app/api/items/route.ts`, DB 모델, FE의 `fetch` 및 기존 테스트를 찾는다. 기존 계약이 다르면 이 예시가 아닌 기존 계약을 따른다.
2. JSON 파싱과 `name`의 타입·필수 여부를 확인한다. 문자열 길이 제한이나 공백 처리 정책은 실제 계약이 없으면 확인한다. 인증·소유권이 요구된다면 서버에서 확인한다.
3. 제공된 DB client로 저장하고 반환된 실제 레코드를 계약대로 응답한다. 예외를 무시한 성공 응답이나 프로세스 메모리만의 저장으로 대체하지 않는다.
4. 유효 요청의 상태·본문을 확인하고 **별도 조회로 저장된 값**을 확인한다. 빈 이름 거부 정책이 확정된 경우 잘못된 입력에 대한 응답과 미저장을 확인한다. 저장 오류는 유효 입력을 준비해 격리된 테스트에서 별도로 확인한다.
5. 화면에서 실제 응답의 `item`을 소비하는지 보고, 허용된 미리보기에서 응시자가 직접 제출 후 새로고침한다. 서버 HTTP, DB, 수동 화면 중 실행하지 못한 것은 각각 미검증으로 적는다.

## 6. 캐시·환경 변수·런타임

- Next의 `GET` 응답·`fetch`·페이지 렌더링·클라이언트 캐시는 서로 다르며 버전과 설정에 따라 기본값이 바뀔 수 있다. 쓰기 후 갱신 여부는 프로젝트의 실제 설정과 테스트로 확인한다. 모든 경로에 임의의 캐시 옵션이나 `revalidate`를 넣지 않는다.
- 인증 정보와 비밀은 서버에 둔다. `NEXT_PUBLIC_` 접두사가 붙은 값은 클라이언트 번들에 포함될 수 있으므로 비밀값에 쓰지 않는다. 환경 변수 **값을 출력하거나 공유하지 않는다**. 필수 변수가 제공되지 않았다면 이름·필요 이유와 미검증을 보고한다.
- DB driver, 파일 시스템 또는 Node 전용 라이브러리가 필요할 때 기존 `runtime`과 해당 라이브러리 호환성을 확인한다. Node/Edge 설정을 무작정 변경하지 않는다. 메모리·CPU 제한과 실제 과제 환경을 확인한다.

## 7. 테스트 순서와 진단

1. 제공된 테스트·타입 검사·빌드 명령을 확인하고 관련 명령을 실행한다. 기존 실패와 이번 수정의 실패를 구분한다.
2. 엔드포인트의 정상, 잘못된 JSON/필수값, 없음, 서버 오류, 권한(해당 시)을 실제 계약에 따라 확인한다. 응답의 상태·본문뿐 아니라 저장/미저장 상태도 확인한다.
3. 제공된 미리보기에서 응시자가 수동으로 화면 입력 → API → 결과 → 새로고침/재조회(요구 시)를 확인한다. 자동 브라우저 조작·화면 캡처는 하지 않는다.
4. 실패 시 `화면 입력 → 요청 method/경로 → 핸들러 → 검증 → DB/의존성 → 응답 필드 → 화면` 경계에서 로그와 조건을 확인하고 한 가설씩 검증한다. 실패 수정 후 **같은 요청**을 다시 실행한다.
5. 테스트 더블, handler 직접 호출, 실제 Next 서버 HTTP, 실제 DB, 수동 UI는 다른 근거다. 실행하지 않은 층을 통과라고 보고하지 않는다.

### 빠른 진단표

| 증상 | 먼저 확인 | 흔한 원인 |
| --- | --- | --- |
| 404 | `app/api/.../route.ts` 위치, 실제 URL, App/Pages Router | 경로·파일명 불일치 |
| 405 | 요청 method와 handler의 export | `POST` 호출인데 `GET`만 구현 |
| 400 | 요청 JSON·필드·타입과 검증 결과 | FE가 숫자 대신 문자열을 전송, 필수 필드 누락 |
| 500 | 서버 로그의 오류 위치와 DB/환경 설정 존재 여부 | 파싱 예외, DB 연결 실패, 잘못된 필드 참조 |
| 성공 응답인데 화면이 비어 있음 | 응답 본문, 클라이언트 래퍼와 FE가 배열로 소비하는 값 | 본문의 배열 필드와 FE가 실제로 소비하는 필드 불일치 |
| 저장 후 새로고침하면 사라짐 | 실제 DB 기록·재조회·프로세스 저장 방식 | mock 또는 메모리만 변경 |
| 갱신했는데 이전 데이터가 보임 | 재조회 결과·서버/클라이언트 캐시 경계 | 실제 조회 또는 무효화가 수행되지 않음 |

모든 항목은 가능한 원인일 뿐이다. 실제 오류·응답을 보고 확인한 뒤 수정한다. 비밀값이나 요청 데이터 전문을 로그에 출력하지 않는다.

### 로컬 HTTP로 확인하는 예시

과제에서 로컬 서버 실행과 루프백 요청이 허용되고, 제공 환경의 서버가 실행 중이며, 위 가상 계산 예제를 `/api/calculation`에 연결한 경우에만 아래를 사용할 수 있다. 포트·경로는 실제 서버 안내에 맞게 바꾼다. 외부 주소에 시험 데이터나 결과물을 보내지 않는다.

```sh
curl -i http://localhost:3000/api/calculation \
  -H 'Content-Type: application/json' \
  -d '{"quantity":2,"unitPrice":5000}'
```

200과 `{"total":10000}`을 확인한다. `curl` 응답이 예상과 다르면 실제 서버 로그와 계약을 보고 진단한다. 이 한 요청만으로 잘못된 입력·DB·인증까지 검증됐다고 할 수 없다.

이 폴더의 계산 예시는 Node 22.6+에서 `node --experimental-strip-types --test route.test.mjs`로 직접 함수 호출 테스트가 가능하다. 단, 시험에 제공된 Node 버전·옵션이 이를 지원하는지는 확인되지 않았다. 예시 때문에 Node를 업데이트하거나 패키지를 설치하지 않는다.
