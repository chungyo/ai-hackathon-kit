# BE 구현 결정표

## 1. 요청·상태·실패를 먼저 적는다

관련 기능마다 과제/기존 계약을 근거로 `입력·필수값 → 인증/인가(해당 시) → 업무 규칙 → 저장/조회 → 응답 → 실패 시 데이터 상태`를 확인한다. 코드·문서에 없는 상태 코드나 오류 형식은 기존 패턴을 우선하고 임의로 확정한 경우 가정으로 표시한다.

| 경계 | 확인할 질문 | 대표 검증 |
| --- | --- | --- |
| 입력 | 형식·범위·필수값이 맞는가 | 잘못된 타입, 누락, 허용 경계 |
| 권한 | 해당 데이터에 접근할 수 있는가 | 인증/인가가 요구될 때만 거부 조건 |
| 업무 규칙 | 현재 상태에서 행동이 가능한가 | 이미 종료·중복 요청·존재하지 않는 대상 |
| 저장 | 응답과 DB 상태가 일치하는가 | 성공 후 저장, 실패 시 미저장 또는 롤백 |
| 외부 의존성 | 실패가 성공으로 바뀌지 않는가 | 타임아웃·실패, 로컬 mock과 실제 연동 구분 |
| 출력 | 응답 형식·민감 정보가 적절한가 | 상태·필드·오류, 비밀번호·키 미노출 |

HTTP API라면 제공된 계약을 우선한다. 계약이 없는 예시에서만 다음을 검토한다: 잘못된 입력은 4xx와 수정 가능한 오류, 없는 대상은 해당 조건에 맞는 4xx, 서버/저장 실패는 5xx와 일반화된 오류. 모든 예외를 200으로 바꾸지 않고 스택·시크릿을 응답에 노출하지 않는다. 실제 코드의 기존 API 계약을 임의 변경하지 않는다.

필요한 테스트를 선택한다. 단순 읽기 API에 임의의 쓰기 방어·분산 시스템을 만들지 않는다. 데이터 변경·권한·중복이 중요하면 정상 테스트 하나로 끝내지 않는다.

## 2. 쓰기 정합성과 재시도

- 두 개 이상의 DB 변경이 하나의 업무 결과로 모두 성공하거나 실패해야 한다면 같은 트랜잭션을 검토하고, 실패 시 일부만 저장되지 않는지 확인한다. 읽기만 하면 필요한 구조만 둔다.
- 결제나 실제 외부 호출처럼 되돌리기 어려운 작업은 응답이 없다는 이유로 무조건 재시도하지 않는다. 결과 확인·중복 방지 수단이 실제로 제공되는지 확인한다. 과제 범위 밖 시스템을 임의로 연결하지 않는다.
- 로그에 요청 전체, 인증 헤더, 개인 데이터, 과제 파일을 출력하지 않는다. 필요한 경우 비밀이 아닌 오류 유형과 실제 상태만 남긴다.
- SQL 또는 명령을 동적으로 구성할 때 입력을 그대로 실행 문자열에 이어 붙이지 말고 사용 중인 라이브러리의 파라미터 방식과 검증을 사용한다.

가상 사례: 주문 상태 변경 후 이력 저장이 실패한다. 요구사항이 '둘 다 저장 또는 둘 다 미저장'이라면 기존 DB의 트랜잭션으로 묶고, 성공 케이스와 이력 저장 실패 시 상태를 각각 확인한다. 그런 원자성이 요구되지 않는다면 임의로 정책을 확정하지 않는다.

## 3. FE와 연결·검증

실제 응답 필드·타입·상태와 FE의 소비 위치를 함께 확인한다. 테스트 더블을 사용한 단위 검증, 로컬 DB 통합 검증, 실제 제공 API 연결은 서로 다른 증거다. 환경 제약으로 할 수 없는 검사는 차단 원인과 영향을 기록한다. 시험 자료·결과물을 외부로 보내거나 환경 제한을 우회하지 않는다.
