# Next.js에서 데이터 처리와 저장 흐름 이해하기

이 안내는 Next.js App Router를 사용하는 시간 제한 과제를 위한 것이다. 실제 문제·데이터 명세·출력 계약·제공 버전과 시험 규정이 우선이다. 예시 결과나 정책을 실제 과제의 정답으로 사용하지 않는다. Pages Router라면 기존 `pages/api` 방식을 따른다. 화면 자동화·외부 전송·시험의 파일 선택창/업로드 제한을 우회하지 않는다.

## 1. 먼저 시스템을 한 줄로 설명한다

```text
화면 입력 → 서버 진입점 → 입력·권한 검증 → 데이터 읽기·계산
         → 필요한 경우 DB 저장 → 응답 → 화면 결과
```

| 경계 | 무슨 일을 하나 | 확인할 것 |
| --- | --- | --- |
| 화면 | 입력·진행·오류·결과를 표시 | 버튼이 실제 요청과 연결되는가? |
| Route Handler 또는 Server Action | 요청 수신, 검증·인가, 서비스 호출과 응답 | 현재 프로젝트의 경로·method·요청/응답 계약은 무엇인가? |
| 계산 함수 | 실제 입력으로 업무 규칙을 적용 | 날짜·단위·필수 조건과 품질 기준을 구분하는가? |
| DB | 데이터와 필요한 결과를 저장·조회 | 실패 시 전후 상태와 재시작 후 지속성을 요구하는가? |
| 화면 갱신 | 서버가 실제 반환한 결과를 보여 줌 | 실패·빈 결과·이전 결과를 성공처럼 표시하지 않는가? |

초기 서버 조회는 기존 서버 데이터 함수나 DB를 직접 호출하는 방법을 검토하고, 클라이언트 HTTP 호출은 Route Handler를 검토한다. 기존 패턴이 있으면 우선한다. Server Action도 서버 입력 검증과 인가가 필요하다. 클라이언트 캐시 라이브러리는 요구가 있을 때만 선택한다.

## 2. 데이터셋 적용부터 재계산까지

1. 데이터 명세와 실제 제공 파일을 읽고 필수 열·ID 관계·단위·날짜·값의 의미를 확인한다. 일부만 조사했다면 표본 범위로 보고하고 불확실한 업무 의미는 담당자에게 질문한다.
2. CSV가 있다면 실제 CSV 규칙과 인코딩을 지원하는 **프로젝트에 이미 있는** 파서를 우선 검토한다. 쉼표로 단순 분할하면 인용부호·줄바꿈이 있는 CSV를 잘못 처리할 수 있다. 필요한 패키지의 사용 가능성과 설치 규정을 확인한다. 화면 업로드 금지라면 준비된 서버 측 데이터셋 선택 등 과제에 허용된 경로를 사용한다.
3. 선택한 데이터의 형식과 참조 관계를 실제 입력으로 검증하고, 문제에서 요구한 단위의 오류를 표시한다. 원문이 전체 거부를 요구한다면 잘못된 일부만 적용하지 않는다. 임의의 ID·정책·정답을 코드에 고정하지 않는다.
4. 여러 DB 쓰기가 하나의 적용이어야 한다면 DB가 지원하는 트랜잭션을 사용해 데이터와 현재 적용 상태가 함께 바뀌도록 설계한다. 잘못된 입력과 DB 쓰기 실패는 서로 다른 경로이므로 각각 실제 전후 상태를 확인한다.
5. 결과에 계산 입력의 데이터셋 식별자·버전과 조건을 연결한다. 새 데이터를 적용했지만 계산 전이면 이전 결과를 새 결과로 표시하지 않는다. 계산 도중 입력이 바뀔 수 있다면 현재 버전 확인과 결과 등록이 경합 없이 이루어지는지 DB의 실제 제약·트랜잭션 또는 조건부 갱신을 확인한다. 문제가 정하지 않은 충돌 정책은 확인한다.
6. 실제 요구에 맞게 결과를 계산·저장하고 조회한다. 계산 품질이나 성능은 실제 입력에서 측정하며 최적해를 증명하지 못했다면 그 한계를 밝힌다. 검증기는 무엇을 확인하고 무엇을 확인하지 않는지도 기록한다.

## 3. 실행 가능한 가상 학습 예제

[next-dataset 예제](../examples/next-dataset/route.test.mjs)는 `route.ts`의 `GET`/`POST`를 **직접 호출**하고, SQLite 파일에 데이터셋과 계산 결과를 저장한다. 가상의 데이터는 JSON이며 실제 CSV·인증·실제 과제의 노선 계산·출력 스키마를 구현하지 않는다. 응시 플랫폼에 이 예제나 `node:sqlite`가 있다고 가정하지 않는다.

```text
apply 요청: datasetId와 items
  → route.ts: 입력 검증
  → store.ts: 여러 쓰기를 트랜잭션으로 적용
  → 현재 버전의 계산 결과가 없으면 needs-calculation

calculate 요청
  → 현재 데이터셋 항목을 합산해 같은 버전의 결과 저장
  → GET: 현재 데이터셋과 일치하는 결과만 조회
```

예제의 `store.ts`는 Node의 동기 SQLite API를 사용한다. Node 22.23.1에서 실험적 API 경고가 표시되며, 버전·플래그·빌드 설정에 따라 지원되지 않을 수 있다. 동기 작업과 쓰기 트랜잭션을 길게 유지하는 방식은 대량 데이터나 장시간 계산에 적합하다고 가정하면 안 된다. 시험이나 운영의 Node를 임의로 변경하지 말고 제공된 DB·드라이버를 우선한다.

예제 디렉터리에서 로컬 연습으로 실행한다.

```sh
node --experimental-strip-types --test route.test.mjs
```

테스트는 정상 적용·계산, 별도 Node 프로세스에서 DB 파일 재조회, 잘못된 입력과 중복 ID, 데이터셋 교체 후 이전 결과 미노출, 실제 SQLite 쓰기 실패 시 롤백, 잘못된 JSON을 확인한다. 실제 Next 서버 HTTP, 브라우저, 인증, Docker, Next 서버 재시작, 동시 요청은 이 테스트의 범위가 아니다. 별도 프로세스에서 DB 파일을 읽었다는 결과와 실제 서비스 재시작 검증은 다르다.

별도 로컬 점검에서는 이 예제 파일을 임시 Next.js 16.4.3 App Router 프로젝트에 연결하고 Node 22.23.1에서 빌드, HTTP 요청과 서버 재시작 후 DB 재조회를 확인했다. TypeScript 설정에서 `.ts` import를 허용했다. 이 점검은 예제의 자동 테스트와 별개이며 임시 구성·가상 데이터에 한정된다. 실제 시험·브라우저·인증·Docker·동시 요청은 확인하지 않았다. 상세 관찰은 저장소의 `evaluation/RESULTS.md`를 참고한다.

예제 파일은 Next 라우팅 없이 Node에서 직접 읽는 학습용이다. 실제 프로젝트에 옮길 때는 설치된 Next·TypeScript의 경로·import 설정, Node runtime, 기존 DB 초기화와 인증을 맞추어야 한다. 예제의 고정 동작·에러 메시지·스키마를 과제의 계약으로 취급하지 않는다.

## 4. 구현 후 사용자에게 설명할 내용

기능 단위마다 `build-small`의 설명 형식으로 다음을 실제 파일·함수와 실행 결과에 연결한다.

- **요구와 동작**: 사용자 입력이 어디서 검증되고 어떤 데이터로 어떤 결과를 만드는가?
- **선택 이유**: 이 데이터 구조·저장·계산 방법을 고른 실제 이유와 제한은 무엇인가?
- **실패와 상태**: 잘못된 입력 또는 저장 실패 때 화면·DB의 이전 데이터는 어떻게 되는가?
- **검증과 미확인**: 어떤 입력·명령에서 기대와 실제가 무엇이었는가? handler 직접 호출·실제 HTTP·DB·화면·재시작·Docker 중 어느 수준을 확인했는가?

답을 이해하기 쉬운 말로 짧게 전달하고, 사용자가 선택했다고 확인되지 않은 AI 제안이나 실제로 실행하지 않은 테스트를 만들지 않는다. 후속 서술형에서의 AI·자료 사용은 해당 시험 규정을 따른다.
