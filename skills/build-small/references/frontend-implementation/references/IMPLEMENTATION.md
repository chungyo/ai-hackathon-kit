# FE 구현 결정표

## 1. 서버 상태와 화면 상태

| 상황 | 판단·구현 | 위험 |
| --- | --- | --- |
| 최초 조회 | 로딩 → 결과 또는 오류를 구분하고 재시도 경로를 제공 | 오류를 빈 목록으로 표시 |
| 검색·필터 | 입력과 요청 조건, 표시 결과·카운트가 같은 기준인지 확인 | 먼저 보낸 느린 응답이 최신 검색을 덮음 |
| 폼 제출 | 필드 유효성 → 요청 중 → 결과/실패; 전송 중 중복 제출 방지 | 버튼 클릭 차단만 하고 서버 중복 처리 보장으로 착각 |
| 실패 후 재시도 | 입력을 유지하고 실패 위치와 다음 행동을 보여줌 | 실패인데 성공 토스트 표시 |
| 변경 후 목록 갱신 | 실제 응답을 반영하거나 재조회; 실패 시 기존 상태와 일치시킴 | 로컬에서만 성공처럼 표시 |

기존 서버 상태 라이브러리가 있으면 기존 규칙을 따르고, 없으면 가장 간단한 방법으로 구현한다. 입력 state와 서버 결과는 서로 다른 책임이다. 파생할 수 있는 값은 근거 없이 중복 저장하지 않는다. 과도한 추상화·전역 상태·새 패키지는 필수일 때만 검토한다.

변경 후 화면이 의존하는 목록·상세·집계가 함께 바뀌는지 확인하고, 실제 서버 응답을 반영하거나 영향을 받는 결과를 재조회한다. 서버 상태 캐시가 이미 있다면 요청 조건별 키와 갱신 범위를 점검한다. 즉시 반영이 꼭 필요하고 실패 시 복구를 설계할 수 있을 때만 낙관적 갱신을 검토한다. 이는 특정 라이브러리 추가나 특정 폴더 구조를 뜻하지 않는다.

## 2. 요청과 응답을 연결하기

- 실제 경로, HTTP method, body, 응답 필드·상태 코드, null/빈 배열, 단위를 기존 계약과 비교한다. 이름만 비슷한 필드를 추측해 매핑하지 않는다.
- 유저가 입력한 값을 그대로 표시하지 말고 서버가 반환한 결과를 기준으로 성공을 판단한다. 에러 객체·HTTP 상태를 분리하고 실패를 잡아 빈 성공으로 바꾸지 않는다.
- 시간에 따라 값이 바뀌는 검색은 취소 가능한 요청을 취소하거나 최신 요청 ID를 확인한다. 취소는 이미 시작된 서버 쓰기를 반드시 취소한다고 가정하지 않는다.
- React를 실제로 쓰는 경우 이전 값에 의존하는 상태 수정은 함수형 갱신을 고려하고, effect는 외부 시스템과의 동기화에 사용한다. 매 렌더마다 파생값을 state에 다시 쓰거나 의존성을 숨기는 방식은 피한다. 기존 프로젝트 패턴이 우선이다.

가상 사례: `/api/orders`의 응답 본문이 `{items: []}`인데 화면이 **본문의** `data` 필드를 배열로 읽으면 필드가 맞지 않는다. HTTP 클라이언트의 `response.data`가 본문 자체를 감싼 것일 수도 있으므로 실제 객체와 배열 소비 위치를 먼저 확인한다. 타입만 고치지 말고 실제 응답·UI 표시·빈 결과·에러를 함께 확인한다. 경로와 필드는 예시이지 실제 시험 계약이 아니다.

React를 이미 사용하는 프로젝트의 **요청 취소 예시**다. 요청 주소·응답은 실제 계약에 맞춰 바꾸고, 서버 상태 라이브러리가 있으면 그 취소·캐시 패턴을 우선한다.

```tsx
useEffect(() => {
  const controller = new AbortController();
  setLoading(true);
  setError(null);
  async function load() {
    try {
      const response = await fetch(`/api/orders?q=${encodeURIComponent(query)}`, {
        signal: controller.signal,
      });
      if (!response.ok) throw new Error(`조회 실패 (${response.status})`);
      const result = await response.json();
      if (!controller.signal.aborted) setItems(result.items);
    } catch (error) {
      if (!controller.signal.aborted) setError('조회하지 못했어요. 다시 시도해 주세요.');
    } finally {
      if (!controller.signal.aborted) setLoading(false);
    }
  }
  void load();
  return () => controller.abort();
}, [query]);
```

이 코드는 조회 예시이며 응답 스키마 검증, 재시도 정책, 오류 상세 처리까지 완성한 것이 아니다. 테스트에서 새 검색 응답 뒤 이전 응답이 돌아오는 상황과 취소를 함께 확인한다.

## 3. 검증

1. 관련 테스트와 타입 검사·빌드의 실제 명령을 먼저 확인해 필요한 범위에서 실행한다.
2. 제공된 미리보기에서 응시자가 직접 하나의 핵심 흐름을 입력부터 결과까지 확인한다. 빈 데이터, 유효성 실패, 서버 실패 중 해당하는 항목을 별도로 확인한다.
3. 브라우저 자동화·스크린샷 도구는 사용하지 않는다. 시험 환경에서 수동 조작할 수 없는 상태나 실제 API 연결이 막힌 상태는 미검증으로 보고한다.
4. 빌드 성공은 요청 성공이나 화면 검증을 증명하지 않는다. 반대로 수동 화면 한 번으로 모든 분기와 반응형이 검증된 것은 아니다.
