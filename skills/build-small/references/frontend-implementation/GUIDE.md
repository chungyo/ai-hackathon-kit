# 프론트엔드 구현

과제의 필수 사용자 흐름을 실제 데이터와 동작에 연결한다. 시험 규정과 과제 README가 우선이며 기존 프로젝트의 기술 스택·구조·디자인 시스템을 확인해 따른다. React나 특정 라이브러리, 새 패키지를 기본값으로 도입하지 않는다.

1. README와 관련 화면·라우트·컴포넌트·스타일·데이터 호출·실행 방법을 확인하고 기존 변경을 보존한다. 입력 → 사용자 행동 → 요청 또는 처리 → 결과 표시와 완료 기준을 정한다. 서버/API 계약이 없거나 모호하면 제공된 문서·코드·실무자에게 확인하고 미확인으로 둔다.
2. 필수 흐름 하나를 기존 패턴으로 구현한다. 요청·응답 필드, 타입, 상태 코드, 단위와 오류를 실제 계약에 맞춘다. 테스트용 mock이나 화면 표시만 실제 서버 연동으로 보고하지 않는다. FE와 BE 연결이 필수이고 확인할 수 없다면 해당 요구는 미완료 또는 미검증으로 남긴다.
3. 기능에 필요한 경우 초기·로딩·정상·빈 결과·입력 오류·요청 실패·완료 상태를 분리한다. 오류에는 가능한 복구 방법을 표시하고 실패한 입력을 불필요하게 잃지 않는다. 중복 제출, 오래된 응답에 의한 화면 덮어쓰기, 선택·필터가 바뀌었을 때 데이터 불일치가 해당 기능에 실제로 영향을 줄 때 처리한다.
4. 버튼·링크·폼은 실제 동작에 연결하고 키보드 조작, 명확한 라벨, 포커스와 색 외 단서를 필요한 범위에서 확인한다. 기존 시각 체계와 정보 위계를 우선한다. 시각적 결정이나 화면 상태가 중요하면 `practical-ui`를 함께 참고한다.
5. 제공된 테스트·타입 검사·빌드 중 관련 검증을 실행하고 출력을 확인한다. 제공된 미리보기는 응시자가 직접 조작해 대표 정상 및 실패 흐름을 확인한다. 실행 결과, 실제 API 연결 여부, 수동 UI 확인과 미검증을 구분한다. 시험 중 자동 브라우저 조작·화면 캡처 도구·외부 배포는 하지 않는다.

## 마무리

기능 단위가 끝날 때 `build-small`의 기능별 설명 형식으로 수정한 사용자 흐름·계약, 선택 이유, 실제 검증과 미확인을 간결히 설명한다. 화면만 확인했는지 실제 API까지 확인했는지 구분한다. 여러 스킬을 함께 쓸 때 같은 내용을 중복 보고하지 않는다. 성능 최적화는 실제 병목이나 과제 요구가 있을 때만 하며, 측정하지 않은 성능 향상을 주장하지 않는다.

상태 처리, API 응답 매핑과 경합, 검증 사례는 [FE 구현 결정표](references/IMPLEMENTATION.md)를 읽는다. 시각 설계는 `practical-ui`의 UI 가이드를 따로 읽고, 실제 작동 확인은 `verify-and-fix`로 연결한다.
