# 실무 화면 UI 가이드

이 문서는 기존 프로젝트의 디자인 기준을 대체하지 않는다. 먼저 기존 토큰·폰트·컴포넌트·화면을 찾고, 부족할 때 필요한 부분만 아래 기준을 적용한다. 숫자와 CSS는 디자인이 전혀 없는 웹 앱에서 출발할 수 있는 **예시**이며 브랜드나 접근성 인증 기준이 아니다. 과제의 기기·브랜드·기능이 다르면 조정한다.

## 1. 화면의 역할부터 결정

| 화면 | 먼저 보여줄 것 | 주요 행동 | 피할 것 |
| --- | --- | --- | --- |
| 운영 대시보드 | 판단할 숫자·상태와 기간·데이터 출처 | 항목 보기, 필요한 조치 | 실제 근거 없는 증감률·실시간 배지 |
| 목록·검색 | 검색/필터, 결과 수와 비교에 필요한 속성 | 항목 선택·생성 | 각 행의 본문과 무관한 카드 장식 |
| 입력·신청 | 무엇을 입력하고 무엇이 되는지 | 제출·저장, 필요 시 취소 | 오류 시 입력 삭제, 뜻 없는 비활성 버튼 |
| 분석 결과 | 기준·단위·대상 기간과 결과 | 상세 확인·수정 | 샘플·추정을 실측이나 확정 수치로 표시 |

첫 화면에 제목, 현재 맥락, 주 행동, 실제 핵심 데이터를 배치한다. 섹션은 사용자의 질문이나 행동을 기준으로 나누되 모든 요소를 카드로 감싸지 않는다. 요구사항에 있는 모든 행동은 진입과 결과가 이어져야 한다. 클릭되지 않는 버튼·탭을 완성된 기능처럼 보이게 만들지 않는다.

### 화면 유형별 배치 예시

```text
업무 목록                         상세 또는 입력
┌ 제목 · 한 줄 맥락   [주 행동] ┐   ┌ 뒤로    제목 · 현재 상태 ┐
│ 검색 / 필터 / 결과 수        │   │ 판단에 필요한 핵심 정보 │
│ 이름   상태   갱신일  동작   │   │ 입력 라벨               │
│ 항목   상태   날짜    보기   │   │ [입력]                  │
│ 항목   상태   날짜    보기   │   │ 오류 또는 보조 설명     │
└ 페이지 이동 또는 추가 로드 ──┘   │ [저장]   취소           │
                                   └─────────────────────────┘
```

위 배치는 가상 예시다. 상세가 별도 페이지인지 패널인지, 사용자가 실제로 생성·수정할 수 있는지는 과제의 요구와 기존 UI에 따라 정한다. 본문에 없는 메뉴·지표나 실재하지 않는 데이터를 추가하지 않는다.

## 2. 레이아웃과 간격

- 데스크톱 업무 화면은 내용을 읽을 수 있는 폭을 유지하고 표·필터·상세가 우선이다. 모바일은 열을 줄이고 주요 행동을 순서대로 쌓는다. 2열 배치는 **충분한 가로 공간이 있을 때만** 사용한다.
- 기본 출발점: 페이지 바깥 여백 `24px`(좁은 화면 `16px`), 섹션 간 `24–32px`, 관련 항목 간 `8–12px`, 카드 내부 `16–24px`. 기존 토큰이 있으면 그 값을 쓴다.
- 콘텐츠 최대 폭은 표의 필요 너비를 보면서 정한다. 예시: 읽기형 `72rem`, 데이터 중심 화면은 더 넓게. 사이드바 너비·고정 헤더는 기존 틀에 맞춘다.
- 긴 제목·오류 문구는 높이가 늘어나도록 한다. 단일 행 말줄임은 원문 확인 수단이 있을 때만 사용한다. 표는 좁은 폭에서 핵심 열을 유지하고 가로 스크롤 또는 과제 맥락에 맞는 카드형 전환을 선택한다.
- 고정 버튼·헤더가 마지막 내용, 초점 또는 오류 메시지를 가리지 않는지 직접 확인한다. 임의의 절대 위치나 고정 높이로 콘텐츠 증가를 막지 않는다.

## 3. 색상·타이포그래피

색은 먼저 **역할**에 매핑한다. 기존 색이 없다면 다음과 같이 시작하고 실제 배경/글자 조합을 검증한다. 아래 성공·오류 색은 예시다. 화면 전체에 보편적인 합격을 보장하지 않는다.

```css
:root {
  --page: #f8fafc; --surface: #ffffff; --border: #cbd5e1;
  --text: #0f172a; --text-muted: #475569;
  --primary: #1d4ed8; --on-primary: #ffffff;
  --danger: #b91c1c; --success: #166534;
  --radius-control: 8px; --radius-panel: 12px;
  --focus: #1d4ed8;
}
:focus-visible { outline: 3px solid var(--focus); outline-offset: 2px; }
```

- 기본 본문은 `16px / line-height 1.5` 정도에서 시작한다. 페이지 제목 `24–32px`, 섹션 제목 `18–20px`, 보조 텍스트는 작게만 하지 말고 읽기 좋은 대비를 확보한다. 실제 기기와 기존 체계가 우선이다.
- 한국어는 시스템 폰트나 기존에 포함된 폰트를 우선한다. 긴 한국어·영문·숫자 혼합 텍스트와 숫자의 단위, 자릿수·음수 표시를 확인한다.
- 상태는 색만 쓰지 않고 텍스트·아이콘 등으로 의미를 함께 전달한다. 오류는 인접한 필드나 해당 영역에, 전체 실패는 관련 영역에 설명한다. 빈 결과와 실패를 같은 문구로 처리하지 않는다.
- 명도 대비·포커스는 실제 적용 색상과 배경에서 검사한다. 미검사라면 '접근성 통과'로 표현하지 않는다.
- 참고 기준: WCAG 2.2 AA는 일반 텍스트에 4.5:1, 큰 텍스트에 3:1을 요구한다. 컴포넌트와 상태를 식별하는 데 필요한 비텍스트 시각 정보는 인접 색상과 3:1을 확인한다. 예외와 적용 범위는 [W3C 텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [비텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)를 따른다.
- 위 예시 색상 계산값은 일반 텍스트/흰색 17.85:1, 보조 텍스트/흰색 7.58:1, 흰색/기본 버튼 6.70:1이다. 불투명 단색만 계산한 값이며 이미지·투명도·테두리·상태·실제 렌더링의 검증을 대신하지 않는다.

## 3-1. 빈 프로젝트에서의 최소 화면 뼈대 예시

기존 디자인이 없고 웹 앱이 요구될 때만 참고한다. `--*`는 위 토큰이다. 기존 UI가 있거나 과제 기기가 다르면 사용하지 않는다.

```css
body { margin: 0; background: var(--page); color: var(--text);
       font: 400 1rem/1.5 system-ui, sans-serif; }
.page { width: min(100% - 48px, 72rem); margin-inline: auto; padding-block: 32px; }
.page-heading { display: flex; align-items: flex-start; justify-content: space-between;
                gap: 16px; margin-bottom: 24px; }
.section { margin-block: 24px; }
.panel { background: var(--surface); border: 1px solid var(--border);
         border-radius: var(--radius-panel); padding: 20px; }
.field { display: grid; gap: 6px; }
.field input { box-sizing: border-box; width: 100%; min-height: 44px;
               border: 1px solid #64748b; border-radius: var(--radius-control);
               padding: 10px 12px; color: var(--text); background: var(--surface); }
.button-primary { min-height: 44px; padding: 10px 16px; border: 0;
                  border-radius: var(--radius-control); background: var(--primary);
                  color: var(--on-primary); font: inherit; cursor: pointer; }
.button-primary:disabled { cursor: not-allowed; opacity: .65; }
.help-error { color: var(--danger); }
@media (max-width: 640px) {
  .page { width: calc(100% - 32px); padding-block: 24px; }
  .page-heading { flex-direction: column; }
}
```

이 CSS는 구조 예시일 뿐, 폼 검증·버튼 기능·모달·접근성 통과를 제공하지 않는다. 비활성 상태의 opacity는 실제 배경과 조합에 따라 대비가 바뀌므로 상태별로 검토한다.

## 4. 컴포넌트 동작 기준

| 요소 | 동작·구현 | 확인할 것 |
| --- | --- | --- |
| 버튼 | 행동은 `button`, 이동은 `a`/라우터 링크 | 가능한 행동이 이름으로 이해되는가, 처리 중 중복 제출을 막는가 |
| 입력 | 화면 라벨을 실제 입력에 연결 | 필수 조건·오류가 명확한가, 기존 값이 보존되는가 |
| 오류 | 실패 이유와 가능한 다음 행동 | 필드 오류와 서버 오류를 구분하는가, 비밀정보를 노출하지 않는가 |
| 목록 | 데이터·빈 결과·검색 실패를 구분 | 필터와 표시 개수·상태가 실제 결과와 일치하는가 |
| 확인 대화상자 | 되돌리기 어려운 행동에 한정 | 취소·확인·포커스 이동/복귀를 확인했는가 |
| 숫자·표 | 단위·기간·정렬·0/음수 표시 | 색뿐 아니라 숫자와 상태가 일치하는가 |

버튼은 '확인'만 쓰기보다 실제 행동을 표시한다. 일시적 알림만으로 수정이 필요한 오류를 숨기지 않는다. 로딩으로 전체 페이지를 덮기 전 이전 데이터 유지가 적절한지 판단하고, 유지 중 실패를 보여줄 수 있게 한다.

### 폼 오류 패턴 예시

```html
<label for="title">이름</label>
<input id="title" name="title" aria-describedby="title-error" aria-invalid="true">
<p id="title-error" class="help-error">이름을 입력해 주세요.</p>
```

이 코드는 오류 상태의 마크업 예시다. 오류가 없을 때는 오류 메시지와 연결·`aria-invalid`를 실제 상태에 맞게 변경한다. 서버 오류는 '저장하지 못했어요. 다시 시도해 주세요.'처럼 원인 추측 없이 다음 행동을 제시하고 입력을 유지한다. 오류가 포커스 이동을 요구하는 상황이면 첫 오류 필드에 초점을 옮기는 동작을 실제로 확인한다.

## 5. 과한 기본 디자인 피하기

- 브랜드 근거 없는 거대한 히어로, 'AI' 장식 배지, 번쩍이는 그래디언트, 모든 곳에 같은 둥근 카드, 차트처럼 보이는 가짜 수치는 업무 도구의 판단을 방해한다.
- 그러한 스타일이 항상 금지는 아니다. 과제나 기존 디자인에서 필요하다고 확인되면 해당 요구가 우선한다. 색상명·특정 그림자·코너 값을 일괄 금지하지 않는다.
- 사진·아이콘은 과제에 제공되거나 권한과 사용 조건을 확인한 자산만 사용한다. 시험에서 외부 이미지 검색·자동 캡처·Computer Use를 실행하지 않는다. 필수 이미지가 없으면 임의 대체를 완성이라고 말하지 않는다.

## 6. 수동 확인 표본

제공된 미리보기에서 응시자가 직접: 정상/빈 결과/오류 각각 1회, 긴 라벨 1개, 좁은 폭 1개, Tab 초점·Enter 제출, 새로고침 후 데이터·상태를 해당 기능에 맞게 살펴본다. 모니터 전환·브라우저 화면 이탈이나 금지된 단축키는 사용하지 않는다. 확인하지 않은 상태와 이유를 기록한다.
