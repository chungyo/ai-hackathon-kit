# 작은 단위로 실제 흐름 만들기

필수 요구사항의 실제 사용자 흐름을 먼저 완성하고, 관련 검증을 반복한다. 자동화 도구가 허용되지 않는 상황에서는 제공된 수동 검증 수단을 사용한다.

1. 기존 코드·환경·의존성·실행 명령과 현재 변경사항을 확인한다. 기존 작업을 보존한다.
2. 필수 사용자 행동 하나에 입력, 기대 출력, 성공·실패 조건을 정한다. 관련 요구사항과 확인된 정책에 연결한다. 불필요한 시스템 교체나 추상화를 피한다.
3. 작은 변경으로 입력→처리→출력까지 연결하고, 제공된 테스트와 실제 실행 수단으로 확인한다. 테스트가 필요한 핵심 로직은 정상과 중요한 실패 사례를 검증한다. 별도 도구가 막히면 제공된 범위의 수동 확인을 하고 한계를 남긴다.
4. 결과를 읽고 빠진 조건을 바로잡는다. 이전 흐름이 동작하는 상태를 유지하면서 다음 필수 행동으로 간다. 시간이 부족하면 필수 요건의 미완료 항목을 명확하게 보고한다.
5. 실제 API·저장이 필수인 경우 실행 경로를 확인한다. 연결이 불가능하면 모의 동작을 실제 완료로 가장하지 않는다. mock은 과제가 허용하거나 응시자가 명시적으로 확인한 보조 검증으로만 구분한다.

완료 보고에는 변경한 핵심 흐름, 실행한 명령이나 수동 확인, 관측 결과와 미검증을 적는다. 시험 결과물의 외부 배포·업로드와 시험 환경의 제한 우회·시스템 설정 변경은 하지 않는다.

중요한 단위에서는 실제 요구 ID, 입력→처리→저장/출력의 파일·함수, 화면과 서버의 상태 기준, 실행 근거를 짧게 남긴다. AI가 제안한 내용과 사용자가 실제로 결정·수정한 내용은 확인된 경우에만 구분한다. 세부 기록은 `explain-my-work`의 [판단·검증 근거 기록](../../explain-my-work/references/EVIDENCE.md)을 필요할 때 사용한다.

## 기능 하나를 구현할 때마다 설명

각 기능 단위의 구현과 해당 검증을 마치거나 구체적인 차단을 확인한 직후, 다음 기능으로 넘어가기 전에 사용자에게 짧게 설명한다. 테스트를 작성만 했거나 실행이 막힌 경우도 그대로 보고한다.

1. **요구·동작**: 해결한 요구와 사용자의 입력 → 실제 처리 → 저장/결과, 주요 파일·함수를 쉬운 말로 설명한다. 실제 관련된 실패 시 화면·데이터 상태도 포함한다.
2. **선택 이유**: 실제로 선택한 방식이 확인된 조건에 맞는 이유와 중요한 한계를 적는다. 비교하지 않은 대안이나 사용자가 직접 내리지 않은 결정을 만들어내지 않는다. 기술 용어는 이 기능에 필요한 의미로 짧게 푼다.
3. **검증 결과**: 실제 실행한 명령 또는 허용된 수동 절차, 대표 입력·기대값·관측 결과, 통과/실패와 확인 수준을 밝힌다. 테스트 더블과 실제 DB·API·화면을 구분하고, 실행하지 않은 항목은 이유와 함께 미검증으로 둔다.
4. **사용자 이해**: 사용자가 서술형으로 설명할 때 알아야 할 핵심을 실제 동작에 맞춰 한두 문장으로 정리한다. 이해를 확인했다고 주장하지 말고, 요청하거나 필요한 경우 한 가지 확인 질문을 제안할 수 있다. 대답을 강제하거나 작업을 멈추지 않는다.

설명은 기능의 위험과 복잡도에 맞춰 간결하게 한다. 여러 스킬을 함께 사용하더라도 한 기능에 하나의 설명만 제공한다. 실제 확인되지 않은 구현·관측·판단 주체를 추정하지 않으며, 후속 서술형 단계의 사용 제한은 시험 규정을 따른다.

사용자에게 보여 주는 기능별 설명은 아래 네 항목을 빠뜨리지 않는다. 설명에 한두 문장씩만 필요하더라도 **왜 선택했는지**와 **실제로 확인한 입력·기대·관측**은 별도로 보이게 적는다.

```text
기능·동작: [요구 / 입력 → 처리 → 결과 / 실제 파일·함수]
선택 이유: [이 기능의 확인된 조건과 연결한 이유 / 중요한 한계]
검증: [실제 실행한 명령·절차 / 대표 입력 / 기대값과 실제 관측 / 확인 수준]
남은 확인: [실패·미실행·미검증과 영향, 없으면 확인한 범위 명시]
```

사용자가 직접 설명할 핵심은 위 항목에서 드러나게 한다. 대표 사례를 실행하지 않았다면 추측해 채우지 말고 실제 확인할 수 있었던 범위와 미확인을 적는다. 사용자 수준에 맞춰 전문 용어를 풀고, 후속 서술형 답안은 대신 작성하지 않는다.

## 범위 판단 예시

| 상황 | 먼저 할 일 | 뒤로 미룰 것 |
| --- | --- | --- |
| 화면과 서버가 모두 필수 | 한 기능의 입력→요청→저장/응답→화면을 연결하고 확인 | 별도 디자인 시스템이나 공통 API 프레임워크 |
| 실제 API가 막힘 | 호출 경로·오류를 확인하고 문제 신고 여부를 판단 | mock을 실제 응답처럼 표시하는 일 |
| 시간이 부족함 | 필수 조건과 실패 위험이 큰 흐름, 제출 파일을 확인 | 선택 기능·장식·근거 없는 최적화 |

시간 부족은 필수 기능을 완료로 바꾸는 근거가 아니다. 가능한 범위와 남은 필수 조건을 그대로 남긴다.
