# 시험용 시스템 설계

입력은 과제 원문·PRD·확인된 담당자 답변·제공 계약·현재 환경이다. 산출물은 **요구 → 설계 결정 → 구현 순서 → 검증 기준**이 연결된 짧은 설계다. 원문·담당자 답변·가정·미확정을 구분하고 기존 코드·사용자의 기술 선택을 우선한다.

1. 필수 조건과 대상 사용자, 실제 입력·출력, 변경되는 상태, 제출·실행 제한을 확인한다. 질문의 답에 따라 구조가 달라지면 답변·영향을 기록하고 독립적인 부분부터 진행한다. 요구하지 않은 정책이나 숫자를 확정하지 않는다.
   - 실제 담당자 답변을 관련 요구 ID와 설계 결정에 연결한다. 변경·부분 답변·원문 충돌이 있으면 영향받는 데이터·상태·구현과 기존 검증의 유효성을 다시 확인한다.
2. 기술 선택이 열려 있을 때 현재 런타임·제공 코드·설치 가능성, 데이터·계산, 실행·컨테이너 제약, 경험과 남은 시간을 비교한다. Next.js 단독과 React + FastAPI는 과제에 적합할 때 후보로 삼으며 한쪽을 정답으로 고정하지 않는다. 대안과 이유·확인되지 않은 설치/성능을 짧게 적는다.
3. 핵심 사용자 행동을 입력 → 화면 → 요청/서버 → 검증·처리 → 저장 → 출력으로 연결한다. 실제 과제에 따라 화면·API·계산 로직·저장 중 필요한 경계만 둔다. 각 경계의 데이터 형식·식별자·소유·권한을 확인하고 없는 API 스키마를 사실로 만들지 않는다.
   - 화면 입력·요청 중 상태와 실제 데이터의 최종 기준을 구분하고, 구현 후 실제 파일·함수·저장 위치를 설계와 대조한다. 누가 무엇을 소유하는지 구현 전에는 계획으로 표시한다.
4. 해당하는 정상, 무효 입력, 실패·복구, 결과 없음, 중복·동시 요청과 데이터 교체 시나리오에서 화면·응답·저장 상태를 각각 정한다. 동시성은 버튼 차단이나 트랜잭션 사용만으로 해결되었다고 가정하지 않는다. 과제가 정하지 않은 업무 정책은 미확정으로 둔다.
5. 필수 불변 조건과 품질·최적화 목표를 구분한다. 생성 로직과 결과 검증이 무엇을 확인하는지 적고, 공통 가정에 따른 검증의 한계와 재현할 작은 기준 입력을 정한다. 최적해나 성능 향상은 입증 없이 주장하지 않는다.
   - 중요한 설계에 대해 실제로 고려한 대안·선택 이유·감수한 비용 또는 한계와 확인 가능한 근거를 연결한다. 새 데이터나 조건이 들어올 때 바뀌는 입력·결과·재계산 범위를 확인하고 정책이 없으면 미확정으로 둔다.
6. 필수 사용자 흐름을 우선하는 작은 구현 단위로 나누고, 각 단위에 요구 ID·선행 조건·검증 방법을 붙인다. 시간 부족은 필수 요구를 삭제하는 근거가 아니다. 실제 독립인 분석은 병렬로 가능하지만 정책·계약 미결정 또는 동일 파일·DB 동시 변경은 충돌을 해소한 뒤 진행한다. 추가 세션·도구는 시험에서 허용될 때만 사용한다.

## 결과

`기술 선택과 이유 / 흐름과 데이터·API 계약 / 실패 시 상태 / 요구 ID별 작업과 검증 / 질문·가정·한계`를 제시한다. 기술적 디테일은 사용자에게 필요한 깊이로 설명한다. 설계 예시와 간단한 작성표는 [설계 작업표](DESIGN_WORKSHEET.md)를 필요한 경우 읽는다. 구현은 `build-small`과 적절한 FE/BE 스킬, 요구 대조는 `requirements-verification`에 넘긴다.
