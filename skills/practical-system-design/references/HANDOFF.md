# 구현 전 handoff: 짧은 검토 문서

PRD·설계와 실제 원문·데이터·담당자 답변을 연결해 응시자가 구현 전에 검토할 수 있도록 작성한다. 기본 위치는 과제 작업 공간의 HANDOFF.md이며, 과제에서 문서·경로를 지정하거나 파일 생성을 제한하면 그 지시를 우선한다. 필요한 내용이 기존 PRD·설계 문서에 이미 있다면 중복 작성 대신 연결하고, 결정을 위해 필요한 항목만 요약한다. 상세 분량은 문제와 남은 시간에 맞춘다.

## 내용

- **목표·필수 요구:** 사용자·핵심 동작·입출력·반드시 지킬 규칙과 근거. 필수 요구를 축소하지 않는다.
- **확인·가정·질문:** 원문과 실제 담당자 답변에 있는 내용, 아직 답이 없는 항목, 가정과 그 영향. 받지 않은 답변은 만들지 않는다.
- **구현 선택:** 실제 사용 가능한 기술·선택 이유와 중요한 대안/한계. 확인되지 않은 설치 가능성은 미확인으로 둔다.
- **동작과 상태:** 입력 → 화면 → API/처리 → 저장 → 결과의 필요한 경계와 상태 소유자. 중요한 오류·중복·데이터 변경 시 현재 결과와 저장 상태.
- **작업 순서:** 필수 기능을 사용자 흐름 중심으로 나누고 첫 구현 단위와 선행 조건을 적는다.
- **검증·설명:** 핵심 정상·실패·경계 사례의 입력과 기대 근거, 결과 검증이 확인할 범위와 한계, 실제 실행 전 상태를 명시한다. 계획을 테스트 통과로 표시하지 않는다.

## 검토와 진행

1. 내용을 작성하고 사용자에게 위치와 짧은 요약, 특히 검토해야 할 불확실성·결정을 보여 준다. CLI에서는 과제가 허용하면 cat HANDOFF.md로 다시 볼 수 있게 한다.
2. **응시자의 검토·구현 진행 의사가 명시되기 전에는 제품 코드 구현, 기능 변경, 의존성 설치를 시작하지 않는다.** 단순 시간 경과는 승인이 아니다. 담당자 답변 확인·자료 조사 등 결정에 영향을 받지 않는 읽기 전용 작업은 계속할 수 있다.
3. 수정 요청을 받으면 문서를 고치고 변경점과 남은 미확정을 보여 준다. 사용자가 문서를 검토하고 계속 진행하라고 하거나 구체적으로 구현을 지시하면 그 범위에서 구현한다. 이미 승인된 동일 설계의 각 기능마다 같은 승인을 반복하지 않는다.
4. 실제 담당자 답변이나 필수 요구가 이후 설계를 바꾸면 영향과 기존 검증을 다시 확인하고, 사용자가 새로 검토해야 할 중요한 변경만 알린다. 과제 시간 때문에 임의로 승인을 받은 것으로 처리하지 않는다.
