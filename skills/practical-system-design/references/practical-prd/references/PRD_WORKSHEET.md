# 실무형 PRD 양식

실제 과제의 README·실무자 답변·제공 데이터·계약을 근거로 작성한다. 이 양식은 요구된 산출물 형식을 대체하지 않는다. 복잡하거나 상세 명세가 요청된 과제에서는 관련 항목을 충분히 채우고, 해당하지 않는 항목은 사유를 남긴다. 모든 예시는 가상이며 실제 시험 문제가 아니다.

## 1. 문서 범위와 근거

- 제목 / 작성 시점 / 문서 상태: [초안·검증 대기 등]
- 근거: [README의 절·요구번호, 제공 파일, 실무자 응답]
- 과제 제약: [시간, 제공 기술·데이터, 실행 환경, 제출물]
- 결정되지 않은 충돌: [출처 A와 B·영향·확인할 대상]

## 2. 문제와 목표

| 구분 | 확인할 내용 | 근거·상태 |
| --- | --- | --- |
| 사용자·업무 상황 | 누가 언제 어떤 업무를 수행하는가 | 문서·응답 또는 미확정 |
| 현재 어려움 | 관찰된 불편·오류·작업과 영향은 무엇인가 | 증거와 추론 분리 |
| 해결할 문제 | 무엇이 달라져야 하는가 | 증상과 원인 가설 분리 |
| 성공 조건 | 과제에서 요구한 관찰 가능한 결과는 무엇인가 | 확인 방법·미확정 |
| 범위 밖 | 과제에 없는 기능과 선택 사항은 무엇인가 | 과제 근거 |

측정 기준이 없다면 지표나 목표 수치를 지어내지 않는다. 시간 절감·정확도·비용 등은 실제 기준이나 측정이 있을 때만 수치로 적는다.

## 3. 사용자와 핵심 흐름

| 사용자·상태 | 트리거·목표 | 입력·전제/권한 | 처리·결과 | 다음 상태·저장 | 근거 |
| --- | --- | --- | --- | --- | --- |
| [역할·현재 상태] | [행동] | [입력·조건] | [결과] | [상태·사이드이펙트] | [원문] |

사용자 여정은 시작 → 주요 동작 → 결과로 연결한다. 대상별 조회·생성·수정·취소가 과제에서 요구되는 경우에만 해당 흐름과 권한을 적는다. 단순 화면 목록이나 컴포넌트 import 관계를 사용자 상태 전이로 간주하지 않는다.

## 4. 요구사항과 추적성

| ID | 원문 요구·출처 | 주체 / 행동 / 조건 / 결과 | 유형·필수/선택 | 구현 위치·계약 | 검증 사례·증거 | 구현 상태 | 검증 상태 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| R1 | [원문과 절] | [역할, 입력, 처리, 출력] | [필수/선택] | [미정 또는 파일·계약] | [기준·실행 결과] | 미구현 | 검증 대기 |

유형은 필요한 경우 기능·데이터·UI·API·보안/권한·성능·제출물로 분류한다. 원문 ID가 없으면 임시 ID를 붙인다. 필수 여부가 모호하면 확인 필요로 표시하고 임의로 선택 기능으로 내리지 않는다. 구현 상태는 `미구현 / 부분 구현 / 구현`, 검증 상태는 `검증 대기 / 통과 / 실패 / 미검증`처럼 분리한다.

## 5. 기능 상세 명세

영향이 큰 필수 기능에 아래 항목을 작성한다. 단순한 기능은 추적성 표에 합칠 수 있다.

- **기능·목적 / 요구 ID:** [무엇을 왜 하는가 / 출처]
- **사용자·진입 조건:** [권한·이전 상태·필수 데이터]
- **입력:** [필드·형식·필수 여부·범위·단위·출처]
- **처리와 정책:** [입력 확인 → 계산·분류·처리 → 저장/응답; 근거 없는 규칙은 미확정]
- **출력과 사이드이펙트:** [화면·응답·파일, 데이터 생성·수정, 전후 상태]
- **실패와 복구:** [실제로 관련된 오류, 표시, 유지할 입력·저장 상태, 재시도 조건]
- **관련 UI/API/데이터:** [기존 경로·필드·계약 또는 확인 필요]
- **인수 기준:** [전제·행동·결과와 데이터 상태]

| 현재 상태 | 행동·트리거 | 발생 조건·Guard | 사용자에게 보일 결과 | 저장/외부 영향 | 다음 상태·복구 | 근거 |
| --- | --- | --- | --- | --- | --- | --- |
| [초기] | [제출] | [유효] | [결과] | [저장] | [완료] | [출처] |
| [입력중] | [제출] | [유효하지 않음] | [오류] | [저장 여부] | [입력 유지/수정] | [출처 또는 미확정] |

해당 기능에 맞게 로딩·빈 결과·실패·권한 없음·중복·취소·재시도·경계값을 선택한다. 정책이 없으면 '예외 처리 확인 필요'로 남긴다. UI 버튼의 존재·활성 조건, FE 요청, 서버 Guard, 저장 부작용과 결과를 혼동하지 않는다.

## 8. 인수 기준과 검증 계획

| 사례 ID | 요구 ID | 전제 | 입력·행동 | 기대 화면·응답 | 기대 데이터 상태 | 검증 방법 | 결과·증거 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AC-1 | R1 | [초기 상태] | [행동] | [기대] | [저장/미저장] | [테스트·수동] | 검증 대기 |

기대 결과는 원문·확인된 정책에서 도출한다. 결측·거부·오류 정책이 미확정이면 '기대 결과 확인 필요'로 남기고 해당 요구를 통과시키지 않는다. 단위 테스트, FE/BE 연결, 실제 서버 연결, 수동 화면, 제출 파일은 각각 근거를 기록한다.

| 구분 | 내용 | 구현·검증 영향 | 확인 대상 | 상태·근거 |
| --- | --- | --- | --- | --- |
| 질문 | [구체적인 불확실성] | [달라지는 결정] | [실무자] | [답변 대기/답변] |
| 가정 | [확인되지 않은 현재 선택] | [영향] | [확인 대상] | [근거·제한] |
| 결정 | [실제 선택] | [대안과 이유] | [결정자] | [근거] |

답변이 없으면 임의 확정 없이 영향받지 않는 작업부터 진행한다. 문서가 실무자 답변과 다르면 각각의 출처와 충돌을 남긴다.

## 10. 구현 순서와 제출 전 확인

- 필수 흐름을 작게 나눈다: [요건 → 작업 → 확인].
- 필요한 FE·BE·데이터 의존성과 기존 실행 방법을 확인한다.
- 실제 남은 시간에 맞춰 구현·검증·제출 시간을 남긴다. 선택 기능과 후순위 개선은 별도 기록한다.
- 원문 요구별로 누락 여부와 실제 결과를 대조한다. 기능 존재·테스트 통과·실제 연동·수동 확인을 따로 기록한다.
- 후속 서술형 전에 본인이 입력→처리→결과, 선택 이유, 실패 대응, 실제 검증과 한계를 설명할 수 있는지 확인한다. 후속 서술형에서는 AI와 복사·붙여넣기를 사용하지 않는다.

## 가상 예시: CSV 처리 기능 하나

과제에서 **"담당자가 CSV를 올리고 처리 결과를 확인한다"**는 요구만 확인했다고 가정한다.

- 문제·목표: 담당자가 CSV를 제출하고 결과를 확인해야 한다. 현재 업무 시간이나 오류율은 주어지지 않았다.
- R1(필수): CSV 선택·제출 → 결과 표시. 근거: 가상의 README. 처리 규칙은 문서에서 확인 필요.
- AC-1: 유효한 제공 샘플을 제출하면 계약된 결과가 표시된다. 구체적인 계산값은 실제 요구와 샘플에 근거해 정한다.
- 미확정: 일부 행이 잘못되면 전체를 거부하는지, 유효한 행만 처리하는지. 실무자에게 묻고 답변 전 어느 정책도 확정하지 않는다.
- 검증 대기: 실제 샘플 제출, 오류 데이터 처리, 화면과 서버 결과의 일치. 아직 실행하지 않았다면 통과가 아니다.

## 가상 예시: 요구에서 인수 기준까지

**가상의 원문**: “담당자는 CSV를 업로드하고 유효한 모든 행을 처리한 뒤 결과를 확인한다. 결과는 다시 조회할 수 있어야 한다.” 허용 형식·저장소·혼합 오류 처리 정책은 제공되지 않았다.

| ID | 원문에서 확정된 조건 | 연결될 작업 | 인수 기준과 확인 수준 |
| --- | --- | --- | --- |
| R1 | CSV 업로드 | 선택 → 업로드 요청 → 서버 수신 | 유효 샘플로 요청이 수신되는지 실제 실행; 파일 형식 상세·크기 검증은 계약 확인 필요 |
| R2 | 유효한 모든 행 처리 | 행별 입력·처리 결과 연결 | 제공된 유효 샘플의 각 행과 결과를 대조; 처리 규칙 미제공이면 결과 기대값 확인 대기 |
| R3 | 결과 확인 | 서버 결과 → 화면 표시 | 실제 응답과 화면 표시 일치; mock 화면은 실제 연결 증거가 아님 |
| R4 | 결과 재조회 | 저장 → 조회 → 결과 화면 | 제공된 저장소에 기록한 뒤 별도 요청으로 재조회; 저장소가 없으면 미구현 또는 미검증 |

**질문 Q1**: 오류 행이 섞이면 유효 행을 먼저 처리하고 오류 행을 따로 보여 주나요? 답에 따라 부분 저장·오류 표시·재처리 기준이 달라진다. R2의 유효 행 처리를 삭제하지 않는다. 답이 없으면 혼합 입력의 정책과 AC를 미확정으로 두고 유효 샘플 흐름부터 진행한다.

**결정된 사실과 가정**: R1~R4는 위 가상 원문의 요구다. “부분 저장”, “자동 재시도”, “5 MB 제한”, “처리 성공률 99%”는 이 원문만으로 확정할 수 없다. 필요하면 질문하거나 가정으로 표시한다. 가정에 따라 작성한 코드는 정책 확정 또는 실제 검증을 뜻하지 않는다.

**검증 사례의 예시**: AC-1은 과제에서 제공한 유효 CSV를 업로드했을 때 모든 유효 행의 처리 결과가 표시되는지, AC-2는 결과 ID를 통해 새 요청에서 같은 결과가 조회되는지 확인한다. 결과 ID는 가능한 구현 예시이며 확정된 API 계약이 아니다. 기대값·포맷은 실제 제공된 규칙을 사용한다. 아직 실행하지 않았으므로 둘 다 검증 대기다. AC-3의 혼합 입력 결과는 Q1 답변 전 미확정이다.

이 예시는 기능·계약을 발명하기 위한 템플릿이 아니라 요구 하나가 화면·서버·저장과 여러 검증으로 연결되는 모습을 보여 준다. 현장에서는 실제 계약과 사용 가능한 환경을 따른다.
