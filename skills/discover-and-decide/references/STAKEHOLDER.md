# 실무 담당자에게 질문하고 답변을 연결하기

과제 원문·실제 데이터·담당자의 실제 답변이 기준이다. 모든 예시는 가상이다. 시험의 최신 규정과 플랫폼 안내가 우선하며, 담당자 에이전트가 있는지, 접근·질문 방식과 횟수 제한이 무엇인지는 실제 환경에서 확인한다. 질문 후보를 만든 것과 응시자가 질문해 실제 답변을 받은 것은 다르다. 담당자의 응답을 지어내지 않는다.

## 1. 질문 후보를 발견하기

1. 원문에서 역할·행동·조건·필수 출력과 이미 확정된 규칙을 추출한다. 질문으로 확정 조건을 완화하거나 담당자에게 구현·정답을 대신 요청하지 않는다.
2. 허용된 범위에서 데이터 설명과 실제 샘플·값·관계를 확인한다. 파일/열/행·단위·대상·시각·관측 범위를 기록하고 민감한 원본은 불필요하게 복사하지 않는다. 파일에 예시만 있거나 일부 행만 읽었다면 그 범위를 명시한다.
3. 실제 관찰에서 의미·기준이 갈리는 지점을 찾는다. 예: 날짜가 어떤 사건을 뜻하는지, 빈 값이 무엇을 뜻하는지, 비교 기준이 필수 제한인지 선호인지, 결과 불가 시 어떤 운영 처리가 필요한지. 과제에 관련되지 않는 질문은 만들지 않는다.
4. 각 질문에 `관찰·출처 / 모호한 업무 의미 / 답에 따라 달라질 PRD·설계·구현·검증 / 중요도`를 붙인다. 이미 원문·데이터 설명에 답이 있는지 다시 확인한다. 구현에 대한 불확실성인지 업무 정책의 불확실성인지 구분한다.
5. 영향이 크고 당장 필요한 질문부터 묶는다. 양쪽에 다를 수 있는 가정이나 효과를 자연어로 제시하되 선택지를 정답처럼 유도하지 않는다. 플랫폼의 실제 제한을 우선하고 고정된 질문 수를 강제하지 않는다. 답변 대기 중에는 영향을 받지 않는 작업부터 진행한다.

## 2. 실제 답변을 반영하기

| 구분 | 무엇을 남기는가 |
| --- | --- |
| 질문 | 실제 질문, 관련 요구 ID, 관찰과 출처, 답에 따라 달라지는 처리 |
| 답변 | 실제 받은 내용·대화 위치·확인 범위; 추정한 답변은 기록하지 않음 |
| 조정 | 영향받는 PRD의 인수 기준, 설계의 입력·상태·정책, 코드 위치 또는 구현 계획 |
| 검증 | 답변에 근거한 전제·입력·기대 결과와 실제 실행·관측 여부 |
| 상태 | 답변 대기·부분 답변·확인·충돌, 그리고 PRD/설계/구현/검증의 별도 상태 |

답변이 없거나 일부만 왔으면 나머지는 미확정으로 유지한다. 임시 가정이 필요하면 가정의 영향과 확인 대상을 적고 필수 조건을 완화하지 않는다. 답이 원문·다른 답변과 충돌하면 양쪽 출처와 영향을 기록해 다시 확인한다. 답을 받았다는 사실은 구현이나 테스트가 통과했다는 뜻이 아니다. 새 답변이 이전 선택이나 기대값을 바꾸면 관련 구현과 이전 검증이 여전히 유효한지 재평가하고 필요한 테스트를 다시 수행한다. 이미 과제에 있는 문서와 작업판을 재사용하고 민감 정보를 기록하지 않는다.

## 3. 가상의 사례

가상 데이터 설명에는 날짜 열이 있으나 그 날짜가 업무 시작일인지 완료일인지는 적혀 있지 않다. 일부 샘플에서 시작과 완료 시각이 자정을 넘는다.

- 관찰: 날짜 열이 있고 샘플의 한 작업이 자정을 넘는다. 전체 데이터의 빈도나 날짜의 의미는 미확인이다.
- 질문: “기록의 날짜는 업무 시작일과 완료일 중 무엇을 의미하나요? 자정을 넘긴 작업을 사용자가 어느 날짜로 조회해야 하나요?”
- 영향: 사용자의 날짜 선택, 저장된 기준일과 결과 조회 조건, 경계일 테스트가 달라진다.
- 답변 전: 실제 답변과 기대값은 미확정으로 두고 날짜 해석에 의존하지 않는 데이터 형식 점검을 진행한다.
- 답변 후: 실제 받은 범위에만 근거해 PRD·설계·코드·테스트를 연결한다. 여기서는 답변과 테스트를 수행하지 않았다.
