# 문제 해결 작업표

문제 해결은 조사 범위에 맞춰 가볍게 사용한다. 표를 전부 만들 필요는 없으며, 인수 기준과 필수 산출물은 생략하지 않는다.

## 1. 프레이밍

| 항목 | 질문 | 근거 |
| --- | --- | --- |
| 사용자와 상황 | 누가 어떤 업무를 언제 수행하는가? | 원문·실무자 응답 |
| 증상 | 실제로 관측하거나 제공받은 현상은? | 실행 결과·문서 |
| 영향 | 어떤 결정·행동·데이터에 지장이 생기는가? | 확인된 사실 또는 미확정 |
| 목표 | 무엇이 달라져야 성공인가? | 필수 요구·확인 방법 |
| 경계 | 시간·환경·금지 행동·기존 코드 제약은? | 공지·README |

문제 정의 예시: '담당자가 파일을 제출한 뒤 처리 결과를 확인할 수 있어야 한다.' 처리 속도나 기존 오류율은 측정되지 않았다면 적지 않는다.

## 2. 사실과 의사결정

| ID | 내용 | 분류 | 출처·관측 | 영향/다음 확인 |
| --- | --- | --- | --- | --- |
| F1 | 결과 표시가 필요하다 | 확인된 요구 | README | 필수 UI·계약 |
| H1 | 실패는 서버의 입력 검증에서 발생한다 | 가설 | 오류 증상만 관측 | 요청·서버 응답 확인 |
| U1 | 오류 행이 섞일 때 처리 방식 | 미확정 | 정보 없음 | 실무자에게 질문 |

분류가 바뀌면 실제로 확인한 근거를 남긴다. 일부 사실을 근거로 원인 전체를 확정하지 않는다.

## 3. 옵션 비교

| 선택지 | 필수 요건 충족 | 구현·검증 비용 | 실패 시 영향 | 결정 |
| --- | --- | --- | --- | --- |
| 기존 기능 확장 | 확인 / 미확인 / 불가 | [근거] | [근거] | [선택/제외 이유] |
| 국소 구현 | 확인 / 미확인 / 불가 | [근거] | [근거] | [선택/제외 이유] |
| 구조 변경 | 확인 / 미확인 / 불가 | [근거] | [근거] | [선택/제외 이유] |

필수 조건을 충족하지 못하는 옵션은 시간 절약을 이유로 완료안이 될 수 없다. 코딩, 수동 절차, 데이터 계산 등 실제 과제에 맞는 대안만 비교한다. 과제에 필요한 기술이나 데이터가 정해진 경우 그 제약을 우선한다.

## 4. 오류 진단 가상 예시

- 증상: 화면이 결과 없음이라고 표시한다. 실제 서버 연결은 확인 전이다.
- 가능한 원인: API가 빈 배열 반환 / 화면에서 다른 필드를 읽음 / 요청이 실패함. 모두 가설이다.
- 가장 작은 확인: 제공된 허용 환경에서 요청의 실제 상태와 응답 필드, 화면의 소비 필드를 비교한다.
- 관측: 응답 본문이 `{items: [...]}`이고 UI가 `data`를 읽는다는 것만으로는 부족하다. HTTP 클라이언트의 반환 객체와 목록이 실제로 소비하는 값을 확인해 필드 불일치인지 판단한다. `data`가 응답 본문을 담는 래퍼일 수도 있다.
- 수정 후: 동일 입력으로 결과가 표시되는지 다시 확인하고, 빈 응답·요청 오류도 구분한다.

이 사례의 필드 이름과 데이터는 가상 예시이며 실제 과제 계약으로 복사하지 않는다.

## 5. 시간 압박 시

필수 조건·제출물을 확인하고 핵심 흐름의 가장 큰 위험부터 확인한다. 선택 기능·장식·과도한 추상화는 뒤로 둔다. 완료까지 불가능하면 실제로 확인한 것, 미완료 필수 조건과 막힌 이유를 명시한다. 로그 삭제·위장·외부 업로드·감독 우회는 해결책이 아니다.

## 6. 관측으로 가설을 구분하는 예시

**가상 상황**: 저장 뒤 목록이 비어 있다. UI에는 오류 메시지가 없고, 서버 요청과 데이터 상태는 아직 확인하지 않았다.

| 가설 | 구별할 관찰 | 결과에 따른 다음 행동 |
| --- | --- | --- |
| 요청이 실패했다 | 요청 method·경로·상태를 확인 | 실패 응답이면 핸들러·입력 경계를 조사한다 |
| 요청은 성공했지만 저장되지 않았다 | 안전한 테스트 데이터의 저장·재조회를 확인 | DB 기록이 없다면 쓰기 경로·오류 처리를 조사한다 |
| 재조회에는 값이 있지만 화면 필드를 잘못 읽는다 | 응답 본문, 클라이언트 래퍼와 화면이 배열로 소비하는 값을 비교 | 실제 소비값이 다르면 계약에 맞게 수정하고 같은 흐름을 다시 확인한다 |
| 응답과 화면 계약은 맞지만 오래된 결과다 | 실제 재조회와 클라이언트 상태·캐시를 구분 | 어디가 오래됐는지 확인한 뒤 해당 계층만 수정한다 |

가장 앞선 미확인 경계를 먼저 확인한다. 실제 DB 접근이 차단됐다면 이 표를 그대로 원인 확정에 쓰지 않고 저장 상태를 미검증으로 남긴다. 관련 없는 환경 설정 변경이나 새 DB 연결로 제한을 우회하지 않는다.
