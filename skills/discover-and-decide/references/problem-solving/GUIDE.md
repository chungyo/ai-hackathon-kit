# 문제 해결: 관찰 → 판단 → 실행 → 확인

가장 짧은 구현이 아니라 **확인된 사용자의 문제와 필수 조건을 충족하는 가장 단순한 해결**을 찾는다. 시간제한 때문에 사실 확인을 건너뛰거나 AI가 낸 가설을 실제 원인으로 단정하지 않는다. 시험 규정·최신 공지·과제 README가 우선이다.

## 1. 문제 유형을 구별

| 상황 | 먼저 할 일 | 도착점 |
| --- | --- | --- |
| 요구가 모호하다 | 사용자·업무·필수 결과·미확정 정책을 분리하고 실무자에게 영향 큰 질문을 한다 | 확인된 요구와 명시된 가정 |
| 무엇을 만들지 정해야 한다 | 문제·제약·필수 조건을 기준으로 기존 방식, 작은 변경, 대안을 비교한다 | 검증 가능한 선택과 이유 |
| 이미 기능이 실패한다 | 같은 조건 재현 → 화면·요청·서버·저장의 경계 확인 → 가설 검증 | 확인된 원인 또는 남은 불확실성 |
| 데이터 결과가 의심된다 | 원본·필터·단위·계산·출력 과정을 역추적한다 | 재계산 근거와 한계 |

## 2. 목표와 증거

1. `누가 / 어떤 상황 / 현재 관찰 / 영향 / 원하는 결과 / 필수 제약`을 적고 각 핵심 주장에 README·파일·실무자 응답·실제 실행 결과를 연결한다. 기대가 명확하지 않으면 질문한다.
2. 사실 / 추론 / 가정 / 미확정을 분리한다. 문제가 어디서 시작하는지 모르면 관측할 방법을 먼저 정의한다. 개인적 추측을 현업 정책·진짜 원인·측정 결과처럼 쓰지 않는다.
3. 해결책을 비교할 때 원문 필수 요건을 먼저 통과 조건으로 둔다. 기존 기능·데이터를 활용한 방법, 집중 수정, 더 큰 대안 중 현실적인 것만 보고 구현 시간·실패 영향·검증 가능성을 고려한다. 선택의 이유와 미룬 선택 사항을 간결하게 남긴다.

## 3. 한 번에 하나씩 검증하고 전진

4. 가장 위험하거나 중요한 가정을 먼저 확인한다. 어떤 관측 결과가 가설을 지지하거나 반박할지 적고, 안전하고 허용된 작은 실험을 한다. 결과가 다르면 가설을 수정한다. 이미 있는 작업과 데이터를 보존하고, 과제 데이터·로그를 외부에 보내지 않는다.
   - 데이터 흐름을 따라 마지막 정상 지점과 최초 불일치 지점을 비교한다. 예를 들어 응답에 값이 있는지 확인하기 전 화면 빈 값을 DB 원인으로 확정하지 않는다. 두 가설이 같은 관찰을 예측한다면 둘을 구별할 수 있는 확인을 고른다.
   - HTTP 응답 본문과 클라이언트 라이브러리가 감싼 객체는 다를 수 있다. `response.data`만 보고 코드가 배열을 받는지 본문 전체를 받는지 단정하지 않는다. 실제 객체와 배열을 소비하는 위치를 확인하기 전에는 필드 불일치를 가능한 원인으로만 표시한다.
5. 한 사용자 행동의 입력 → 조건 → 처리 → 화면/응답 → 저장 결과를 끝까지 구현·확인한다. 실패하면 `verify-and-fix`를 사용해 재현 조건과 실제 결과부터 확인하고, 수정 후 같은 조건으로 재검증한다.
6. 시간이나 환경이 부족하면 선택 기능·장식부터 미룬다. 필수 연동을 mock으로 대체해 실제 성공으로 보고하지 않는다. 허용 범위가 막히면 제한을 우회하지 않고 미검증과 영향·문제 신고 필요 여부를 남긴다.
   - 반복 수정이 실패하면 같은 처방을 쌓지 말고 가설과 실제 관측을 다시 비교한다. 재현 불가·환경 차단은 각각 분리하고, 위험한 데이터 변경 없이 확인 가능한 다음 실험을 고른다.
7. 결과를 원문 요구와 대조하고, 실제 수행한 검증·실패·미검증을 분리한다. 구현과 테스트가 성공해도 실제 서버·수동 화면·제출까지 확인된 것으로 확대하지 않는다.

## 전달 방식

`문제와 근거 / 핵심 미확정·질문 / 선택한 접근과 이유 / 수행한 검증과 결과 / 남은 필수 항목`을 짧게 제시한다. 더 복잡한 비교와 예시는 [문제 해결 작업표](references/WORKSHEET.md)를 읽는다. 요구사항과 인수 기준이 많으면 `practical-prd`, 최종 대조에는 `requirements-verification`을 연결한다.
