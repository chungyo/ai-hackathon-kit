# 요구사항에 맞춰 검증하고 수정

테스트의 존재, 테스트 통과, 실제 사용자 흐름 확인, 외부 연동 확인은 서로 다른 근거다. 실행하지 않은 검증은 주장하지 않는다.

1. README의 필수 조건과 제출물 각각에 대해 확인 대상·방법·기대 결과를 정한다. 기존 테스트와 실행 방법을 우선 사용한다.
2. 주요 정상 입력과 결과를 확인하고, 영향이 큰 빈 값·잘못된 입력·권한·중복·상태 전환·연결 실패 중 해당하는 경우를 확인한다. 모든 상황을 일괄 구현하지 말고 실제 과제에 필요한 예외를 선택한다.
3. UI가 있으면 제공된 미리보기에서 응시자가 직접 핵심 입력→처리→결과를 확인한다. 접근·권한 제한이 있으면 우회하지 말고 미검증으로 기록한다. 자동 브라우저 조작이나 화면 캡처 도구를 사용하지 않는다.
4. 오류가 있으면 조건과 관측 결과를 남기고 로그·입출력·최근 변경으로 원인을 좁힌다. 필요하면 작은 가설을 한 번에 하나씩 검증하고 원인에 맞게 수정한다. 원인을 확인하지 못하면 추측을 사실처럼 말하지 않는다.
5. 수정 후 원래 실패한 동일 조건과 관련된 핵심 흐름을 다시 확인한다. 테스트의 기대값을 임의 완화하거나 오류를 숨겨 통과시키지 않는다. 실패가 환경·권한 때문에 재현 불가능하면 그 사실과 영향을 보고한다.
6. 각 항목을 `통과 / 실패 / 미검증 / 해당 없음`으로 구분하고 실행 명령 또는 수동 절차, 실제 결과, 남은 리스크를 적는다. 테스트만 통과했다면 실제 UI·서버 연동도 통과했다고 확대하지 않는다.

시간이 부족하면 모든 주변 사례보다 필수 사용자 흐름, 데이터 정합성, 핵심 실패 조건과 제출 파일 검증을 먼저 한다. 실제 검증보다 보고서를 만드는 데 더 많은 시간을 쓰지 않는다.

상태·데이터·API의 테스트 선택과 오류 분석 예시는 [핵심 흐름 검증표](references/TEST_MATRIX.md)를 읽는다.
