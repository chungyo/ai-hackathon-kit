# 요구사항·인수 기준 검증

원문에서 요구한 결과와 실제 관측을 대조한다. 구현이 존재한다는 사실, 테스트가 존재한다는 사실, 테스트가 통과했다는 사실, 실제 환경에서 요구가 충족됐다는 사실은 각각 다르다.

## 1. 기준과 대상 수집

1. README·과제 지시·확인된 실무자 답변과 최신 공지에서 필수 요구, 조건, 제출물, 데이터·출력 형식, 검증 기준을 확인한다. 각 요구에 원문 ID 또는 임시 ID와 출처를 붙인다. 서로 충돌하는 기준과 미확정 정책을 표시한다.
   - 담당자 답변에 따라 달라진 기대값은 실제 답변·요구 ID에 연결한다. 답변 이후 변경된 코드·데이터·정책에서 이전 테스트가 그대로 유효한지 확인하고 필요한 사례를 다시 실행한다. 답변·계획 자체를 테스트 통과로 취급하지 않는다.
2. 실제 코드·입출력 계약·화면·DB·결과 파일·테스트를 확인해 `요구 → 구현 → 검증`을 연결한다. 요구한 주체·동작·조건·결과 중 어느 하나가 빠졌거나 가짜 데이터로 대체됐다면 미충족 또는 미검증으로 표시한다.

## 2. 케이스 도출

3. 요구의 행동별로 `시작 상태 → 트리거 → 조건/Guard → 처리·부작용 → 결과/다음 상태`를 필요한 범위에서 그린다. FE의 버튼 노출·활성 조건, 서버의 권한/유효성 검증, DB 상태와 외부 의존성은 별개의 경계다. 실제 요구와 관계없는 상태·테스트를 일괄 추가하지 않는다.
4. 각 핵심 조건에서 정상·무효/누락·의미 있는 경계·실패/복구를 선택한다. 테스트 기대 결과는 코드가 현재 하는 일이 아니라 README·확인된 계약·실무자 답변에서 도출한다. 출처가 없는 정책은 미확정으로 두고 적당한 기대값을 만들어 통과시키지 않는다.
   - 여러 조건이 결합된 경우는 결과가 달라지는 조합을 선택한다. 예: 유효 입력 + 저장 실패에서는 오류 응답과 저장 상태를 각각 확인한다. 입력 거부가 먼저 발생한다면 그 실행은 저장 실패 경로의 증거가 아니다.
5. 예를 들어 저장 요구는 성공 응답뿐 아니라 실제 데이터의 생성·변경을, 거부/실패는 저장되지 않았거나 요구에 맞는 상태인지 확인한다. FE 요청·응답과 화면 표시를 연결해 본다. mock, 단위·통합 테스트, 실제 연동, 수동 화면은 별도로 판정한다.
   - 계산 결과의 확인이 필요하면 원문·확인된 정책에서 별도의 기준 입력과 기대값을 도출한다. 생성 로직과 같은 오류·가정을 공유하는 검증기의 한계를 밝히고, 실제 확인한 조건과 확인하지 않은 조건을 나눈다. 데이터·코드가 검증 후 바뀌면 이전 관측의 적용 범위를 재확인한다.

## 3. 실행·판정·후속

6. 제공된 테스트와 실행 방법을 우선해 가능한 확인을 수행한다. 수동 UI는 시험 환경의 허용된 미리보기에서 응시자가 직접 확인한다. 자동 브라우저 조작·화면 캡처·외부 전송·제한 우회는 하지 않는다. 실행하지 못한 항목은 미검증으로 둔다.
7. 요구별로 `구현 상태 / 검증 상태 / 방법·관측 결과 / 남은 영향`을 분리한다. 예: 구현됨 + 실제 API 연결 미검증. 실패를 수정하면 이전 실패와 같은 조건과 관련 정상 조건을 다시 확인하고 그 결과만 보고한다.
   - 다른 사람이 허용된 환경에서 재현할 수 있도록 확인한 입력·전제, 실행 명령 또는 조작, 기대 근거, 실제 관측, 해당 코드·결과 위치를 기록한다. 비밀값·개인정보는 제외한다.
   - 결과의 범위와 근거를 함께 기록한다. 예: `mock 저장소 단위 테스트 통과`와 `실제 DB 저장·재조회 미검증`. 한 요구에 여러 필수 조건이 있고 하나라도 실패하면 실패, 차단되었거나 실행하지 않은 필수 조건이 남으면 전체 통과로 판정하지 않는다.
8. 제출 형식·경로·필수 파일을 README에 따라 확인한다. 사용하지 않은 스킬·민감 정보를 외부로 보내지 않는다. 후속 서술형에는 AI를 사용하지 않는다.

상태 전이·테스트 우선순위·완료 대조 예시는 [검증 작업표](ACCEPTANCE.md)를 읽는다. 원인 조사와 구현 수정은 `verify-and-fix`, 구현 기준 정리는 `practical-prd`를 함께 사용한다.
