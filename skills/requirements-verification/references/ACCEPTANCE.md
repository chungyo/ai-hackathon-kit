문서마다 다르면 차이를 기재한다. 불확실한 부분은 실무자에게 질문하고 추측으로 기대값을 확정하지 않는다. 코드에 현재 구현된 규칙이 요구와 맞는지 별도로 확인한다.

이는 **가상 사례**이며 실제 상태와 정책은 과제에서 확인한다. 가능한 행동의 존재·활성 조건과 수행 후 UI/서버/DB 변화는 구분한다. 단계가 많은 기능만 작성하고 단순 읽기 기능에 무관한 상태를 강요하지 않는다.

## 4. 실행 우선순위

1. README의 필수 제출물과 핵심 사용자 흐름의 정상 동작.
2. 데이터 손실·잘못된 저장·중복 실행·권한·외부 연동 실패 중 과제에 실제로 해당하는 위험.
3. 필수 입력 오류·빈 데이터·상태 표시·복구.
4. 선택 기능과 비핵심 시각 사항.

남은 시간에 따라 검증하지 못한 항목을 생략했다고 완료로 바꾸지 않는다. 자동화되지 않은 검증은 제공 환경에서 응시자가 수동으로 수행하고, 기록된 실제 관측만 근거로 사용한다.

`통과`: 특정 요구·조건을 기대 근거와 실제 결과로 확인. `실패`: 기대와 관측이 다름. `미검증`: 확인하지 못함. `해당 없음`: 원문·범위에 해당하지 않는 근거가 있음. 빌드 성공만으로 UI·실제 연동까지 통과시키지 않는다.

## 6. 실패 경로가 실제로 실행됐는지 확인

입력 검증·인증·DB 쓰기 등 앞선 조건이 실패하면 뒤의 로직은 실행되지 않을 수 있다. 예를 들어 DB 실패 처리를 검증할 때는 **유효한 입력과 필요한 인증**을 준비하고, 안전한 테스트 DB 또는 테스트 더블에서 저장 실패를 재현한다. 응답뿐 아니라 쓰기 전후 상태도 확인한다. 테스트 더블에서 예외 처리를 확인한 결과와 실제 DB 장애 시 동작은 다른 증거다. 의도적인 장애 주입은 격리된 테스트 환경에서만 수행한다.

| 가상 케이스 | 전제·동작 | 기대와 근거 | 관측할 것 | 통과로 말할 범위 |
| --- | --- | --- | --- | --- |
| 정상 저장 | 유효 입력으로 생성 후 재조회 | 제공 계약의 성공 응답과 저장 값 | 상태·본문·별도 조회 | 실제 저장소를 사용한 경우에 한해 해당 조건의 저장과 재조회 |
| 입력 거부 | 필수 필드 누락 | 제공 계약의 거부와 쓰기 없음 | 상태·오류·DB 전후 | 입력 검증 경로; DB 실패 처리는 별도 |
| 저장 실패 | 유효 입력 + 안전한 격리 환경의 저장 실패 | 계약된 오류와 요구된 데이터 상태 | 상태·오류·전후 상태 | 실제 DB 장애 또는 모의 장애 중 수행한 수준만 |
| 권한 거부 | 관련 권한 조건이 명시된 경우 다른 사용자의 리소스에 요청 | 서버 거부와 변경 없음 | 응답·저장 상태 | 테스트한 사용자·리소스 조건만 |

하나의 필수 요구에 정상·실패·재조회가 포함된다면 각각 판정한다. 정상 통과와 실패 미검증을 하나의 초록색 `PASS`로 요약하지 않는다. 계약이나 상태를 확인할 방법이 없는 경우 추정하지 말고 그 이유와 남은 위험을 적는다.
