# 서술형 질문 유형별 확인과 학습

과제 수행 중 또는 제출 직전, 실제 원문·담당자 답변·코드·실행 결과를 바탕으로 이해를 점검한다. 아래는 사진에 나온 질문의 **유형**을 일반화한 예시이며 다음 시험에 같은 질문이 나온다는 보장은 없다. 과제와 무관한 항목은 건너뛴다. 시험에서 지정한 산출물·AI 사용·자료 열람 규칙이 우선이다.

## 시간에 맞춘 준비

먼저 실제 필수 흐름과 위험이 큰 규칙을 살핀다. 시간이 부족하면 주요 설계 하나, 입력부터 결과까지의 흐름 하나, 실패 사례 하나, 실행한 검증 하나와 한계를 우선한다. 대략 5~10분 점검은 예시일 뿐 검증 시간을 대체하지 않는다. 구현 단계에서 남긴 기존 문서와 실제 결과를 재사용한다. 과제에 필수인 제출 파일은 양식을 유지한다.

각 주제마다 실제 코드·명령·관측 결과가 없으면 `미구현`, `실행하지 않음`, `확인 필요`로 표시하고 이유와 영향을 말한다. AI가 대신 모범답안을 지어내거나 구현자의 판단을 만들어내지 않는다. 설명과 질문은 과제 수행 시간 안에 한다.

## 1. 필수 규칙, 설계 선택과 대안

- 질문 느낌: 어떤 제약은 반드시 지켜야 하고, 어떤 지표로 더 나은 결과를 비교했는가? 왜 그 방법을 골랐고 대안과 감수한 비용은 무엇인가?
- 확인: 원문 필수 제약·담당자 답변의 출처, 실제 알고리즘의 입력·처리·출력, 실제 선택한 기준과 조건을 바꾸면 달라지는 결과, 확인한 범위와 한계.
- 공부: 필수 조건과 품질 목표의 차이, 후보 선정·배정·순서 결정의 각 단계. 실제 비교하지 않은 대안이나 최적성을 주장하지 않는다.
- 스스로 설명: `규칙 → 선택한 방식 → 이유 → 실제 검증 → 한계`를 한 사례로 설명한다.
- 연계: `practical-system-design`, `requirements-verification`, 구현을 담당한 스킬.

## 2. 데이터 흐름과 상태 소유

- 질문 느낌: 사용자의 선택부터 서버 처리·저장·다른 역할의 화면에 보이기까지 무엇이 어디를 지나는가? 화면과 DB 중 각각 어떤 상태를 소유하는가?
- 확인: 실제 입력·요청 경로·검증·계산·저장·조회·화면 표시, 역할별 권한, 실제 파일·함수·테이블, 데이터셋·계획의 현재 기준과 변경 시 관계.
- 공부: 프론트의 입력·로딩 상태와 서버/DB에 저장된 상태의 차이. 트랜잭션을 썼다면 실제로 묶인 작업과 해결하지 못하는 경쟁 조건을 구분한다.
- 스스로 설명: 사용자 행동 하나를 처음부터 끝까지 따라가며 각 부분의 책임과 실패 시 상태를 말한다.
- 연계: `practical-system-design`, `build-small`.

## 3. 독립 검증, 구현·가정·미구현

- 질문 느낌: 결과 검증기가 실제로 확인하는 것과 확인하지 못하는 것은? 구현한 것과 가정·미구현을 어떻게 구별하고 다른 사람이 어떻게 재현하는가?
- 확인: 검증 조건과 코드 위치, 요구의 출처, 직접 실행한 명령·입력·기대값·관측, 테스트 수준과 미검증. 생성기와 검증기가 공유하는 전제도 살핀다.
- 공부: 테스트 존재와 실행, mock과 실제 DB·API·화면, 규칙 충족과 전역 최적성은 서로 다른 주장이다. 가능하면 원문이나 사람이 직접 계산한 작은 사례를 기준으로 대조한다.
- 스스로 설명: `검사 항목 / 검사하지 않은 항목 / 실제 실행과 재현 방법`을 구체적으로 말한다.
- 연계: `requirements-verification`.

## 4. 실패·경계·중복 요청과 상태 변화

- 질문 느낌: 잘못된 데이터, 처리 중 다른 요청, 정원 초과나 배정 불가능한 입력에서는 어떻게 동작하는가? 기존 결과와 화면에는 어떤 영향이 있는가?
- 확인: 실제 입력 검증과 오류 응답, 계산 중 상태, 중복·경합 처리, DB의 이전 데이터와 결과, 사용자 화면, 미처리 또는 미검증 경로. 과제에 따라 해당 사례만 선택한다.
- 공부: 거부와 부분 처리, 로딩 중 요청 차단과 서버의 동시성 보장, 트랜잭션이 보장하는 범위의 차이. 미구현 처리를 구현한 것처럼 말하지 않는다.
- 스스로 설명: 사례별로 `입력 → 서버 처리 → 저장 전후 → 화면 → 실제 확인`을 따라간다.
- 연계: `build-small`, `requirements-verification`.

## 5. 추가 데이터와 운영 전 검증

- 질문 느낌: 새로운 일정, 데이터셋, 인원 증가가 들어오면 무엇이 깨지기 쉽고 어떤 입력·지표·독립적 근거로 판단할 것인가?
- 확인: 실제 가정·미검증·병목 후보, 데이터 규모와 변경 범위, 측정할 수 있는 실패율·제약 위반 수·처리 시간 등 과제에 맞는 지표와 재현 방법.
- 공부: 관측한 위험과 추정한 위험, 실행한 테스트와 추가로 할 계획, 정확성 지표와 성능 지표를 구분한다. 측정하지 않은 성능이나 실제 운영 가능성을 주장하지 않는다.
- 스스로 설명: 위험 하나와 바꿀 입력, 기대 결과, 실제 관측 또는 미실행 상태를 연결한다.
- 연계: `requirements-verification`.

## 6. 담당자와 AI 협업

- 질문 느낌: 업무 규칙을 어디서 알았고 AI가 무엇을 정리·구현했는가? 본인이 실제로 수용·수정·기각한 내용과 판단 근거는 무엇인가?
- 확인: 실제 질문·담당자 응답과 출처, AI의 제안, 실제 대화·코드 변경과 사용자 결정, 실행한 테스트·관측, 확인되지 않은 판단 주체.
- 공부: 원문 확정 규칙, 담당자 답변, 임시 가정의 차이. 제안을 받아들인 이유와 한계, 바뀐 규칙이 PRD·설계·구현·검증에 미친 영향.
- 스스로 설명: `발견 경로 → 실제 질문·답변 또는 미확정 → AI 제안 → 내 실제 판단 → 검증 → 한계` 중 일어난 사실만 말한다. 수용·수정·기각이 모두 있었다고 꾸미지 않는다.
- 연계: `discover-and-decide`, `build-small`, `explain-my-work/references/EVIDENCE.md`.

## AI에게 요청하는 짧은 점검 지시

> 실제 README, 구현 코드, 내가 확인한 담당자 답변과 실행 결과를 근거로, 과제에 맞는 서술형 질문 유형을 골라줘. 각 유형에서 내가 확인할 파일·실제 동작·검증 범위와 알아야 할 개념을 짧게 설명해줘. 구현·가정·미구현과 실행·미실행을 구분하고, 내가 직접 설명해 보도록 질문 하나씩 제안해줘. 없는 담당자 답변, 내 결정, 테스트 결과나 최적성을 만들지 말고 시간이 부족하면 핵심 흐름부터 점검해줘.

사용자가 답한 경우에만 실제 코드와 실행 근거로 빠진 부분을 피드백한다. 사용자가 답하지 않았거나 시간이 없으면 이해했다고 판단하지 않고 핵심 확인 항목과 미확인만 남긴다.
